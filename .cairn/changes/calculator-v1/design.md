# Calculator-v1 selected guest design

## Context and scope

The accepted CALC requirements describe an application, not a new language conformance profile. This active design selects a separate `noble calculator` route after M4 and the library/module/text/iteration/error-schema gates. Core-Bootstrap keeps wrapping `I64`; ordinary, cursor, declared-module and LIVE environments do not inherit calculator builtins, memory expansion or preparation allowances. No canonical calculator scenario is promoted by this design. r[CALC-SCOPE-01] r[CALC-GATE-01]

## Decisions

### Pure typed guest, narrow terminal shell

**Choice:** Install checked Noble modules for lexical input, exact numbers, rational normalization, parser/evaluator state, diagnostics and display. Every operation of a line is a freshly checked Noble source submission compiled by the selected Wasm backend. The shell may frame bytes, supply seven nonnegative guest budgets, schedule a guest-certified action kind, observe a bounded typed result and retain accepted line sources. It must not parse an expression, resolve a name, calculate a rational, choose an exact display representation, inspect an opaque guest state, supply filesystem/network/clock/process imports, or convert a native error into a guest result. All guest phases of one candidate line share the same checked ModuleSession, prospective compiler and Wasm worker; their state remains on the guest typed stack. r[CALC-SCOPE-01] r[CALC-BOUND-01]

**Rationale:** A host-only evaluator, separately instantiated one-step stand-ins and host reinjection of private parser/numeric state would satisfy neither the compiled Noble backend nor transactional application contract. Phase boundaries are an implementation device, not a second trust boundary or a reset of an individual compiler preparation's accounting. r[CALC-GATE-01]

### Committed line and byte-exact restore

**Choice:** Keep one committed session: the checked ModuleSession, compiler and Wasm worker, with the opaque State on the guest typed stack. Run all typed phases of a new line directly on it. Only after guest acceptance and budgeted exact formatting succeed, commit: the worker snapshots its whole arena (all 64 memory pages, every function-table entry, every runtime global, the published signature table and its counters) and the host keeps copies of the ModuleSession, the compiler and its own session fields (typed stack, module serial, quiescent and Program-free boundary flags, deferred probe consumer). Every other outcome — guest diagnostic or `ResourceLimit`, native quota or trap, host bound, infrastructure failure — restores both halves to the last commit, and the worker verifies the restored memory, table, globals and signatures against the commit byte for byte. A failed verification, or a worker that died, timed out or desynchronized, ends the session. Terminal write failure after a successful commit does not undo that commit. r[CALC-STATE-02]

**Rationale:** A native quota or trap poisons the instance, and a guest diagnostic consumes the line's State (`swap drop`). Restoring the committed arena removes every effect of the failed line: its cells, Text, table entries and signature IDs are overwritten by committed bytes, and the restored compiler reuses those slots and IDs. The runtime `$generation` global and the compiler generation return together. Restore is a trusted engine operation over bytes the guest itself produced and committed; no guest value selects or supplies it, and the host never synthesizes a cell or retains a guest handle. The worker allocates the arena at its 64-page maximum because Wasm memory cannot shrink: a failed line that grew memory could otherwise never return to the committed size, and a fresh memory cannot be paired with table entries that close over the old one without recompiling every installed module. Of the two engine precedents, live publication rolls back but stays terminal, because its failure means installing an already-validated module broke an engine invariant; live proposal inspection continues after a verified rollback, because refusing untrusted guest data is an expected outcome. A failed calculator line is the second kind, so the session continues after a verified restore; a failed verification is the first kind and terminal. A line therefore costs only its own guest modules, however many definitions were admitted, and the former replay limits (64 commands, 65,536 history bytes, replay work) no longer exist. Host transport limits remain labeled separately from the seven guest `ResourceLimit` categories. r[CALC-STATE-02] r[CALC-LIMIT-01]

### Independent selected compiler and memory bounds

**Choice:** The selected source compiler checks borrowed structure, concrete substitutions, complete definition/environment closure, each independent kernel acceptance and identity before publishing a compiler state. It separately bounds 512 reachable named bodies and 896 environment rows, including derived nominal operations; every reachable row retains independent kernel replay. Only during calculator borrowed preflight, before any owned kernel witness clone, each nonzero `Work::charge(amount)` first grants exactly that measured amount through the checked calculator ledger. This preserves the request's original preparation allowance (currently at most 512,000,000 units) for admission and kernel acceptance. The borrowed-preflight grant scope ends before admission; it does not mark the whole submission trusted or enable plan grants across kernel clones. The existing finite environment-work allowance follows environment validation, and only after independent kernel acceptance and identity may plan lowering issue measured shortfalls. All grants and the original allowance share one cumulative ceiling of 2,000,000,000 issued units per preparation. These units bound charged structural operations, **not** a physical CPU/time guarantee. Separate per-type, stack, source, signature and emission caps still reject submissions without raising the work cap. The calculator-only managed runtime imports 16 initial pages and at most 64 pages; at most 72,362 48-byte cell handles fill its disjoint regions up to the exclusive 4 MiB end. Within a submission handles are retained monotonically; only the order-preserving boundary compaction under *Risks and boundaries* reclaims cells, and a handle is valid only until the next submission. The per-invocation allocation limit remains 1,376,208 bytes; no expanded ordinary memory is implied. Text and transient signature-observation scratch stay distinct and observed signatures are copied before scratch reuse. Ordinary and cursor memory remain at their established 16-page maximum. r[CALC-BOUND-01] r[CALC-LIMIT-01] r[CALC-GATE-01]

**Rationale:** Forged direct submissions and deeply expanded type witnesses must not bypass independent checking or disguise physical preclone work; calculator's larger exact-number closure cannot consume ordinary profile authority or memory. Borrowed per-appearance and named-body scans are charged cumulatively; only the exceptional first stack mismatch is reserved once, against the maximum of each actual join's frame/input pair and each root, named or quotation completion's frame/claimed-output pair, never against unrelated frames or heights. A selected backend exhaustion, assembly refusal, engine trap, timeout or host transport bound is never relabeled as deterministic guest `ResourceLimit`. r[CALC-LIMIT-01]

### Exact canonical-epoch module reuse

**Choice:** The compiler boundary above checks every *new* preparation in full. A calculator module may additionally reuse an artifact that boundary already checked, when everything its preparation depends on is exactly equal. The host keeps a process-wide cache keyed by the namespace recipe (the constant calculator module and import sources every session namespace is built from), the exact module source bytes, the exact input stack types and the committed compiler's *canonical epoch*; every component is compared in full and a hash only selects a bucket. A canonical epoch exists only for a calculator compiler without live, slot, text-cursor state or code spans, and only a Program-free preparation is recorded or reused: `prepare_program_free` restarts function allocation at base 5 and starts an empty identity ledger, signature pool and descriptor table, so its WAT, prospective state, issued Work and refusal depend on the committed compiler only through whether it is still at generation 0 (the module that installs the core table entries) and the never-rewound static literal Text cursor `text_end` and content-addressed literal table (`static_literals`; see *Compile-cost headroom*). Those values are the epoch; the table is compared in full, because an equal cursor does not imply equal literal addresses. Calculator modules no longer bake the compiler generation into the `submit` guard: each module imports an immutable `submit_generation` global that the trusted engine binds per instance to the generation the host validated the module against (`Prepared::submit_generation`), and the guard still fails with status 4 unless the arena's `generation` equals it; ordinary, cursor, declared and live modules keep their baked guard. `Compiler::reuse_program_free` refuses any compiler whose epoch differs from the recorded one; it returns the recorded WAT and prospective state with only the generation (not in the bytes) and retention revision taken from the current compiler, and commit applies the unchanged base/provenance checks. A hit skips the source check, the backend and the namespace commit: an Expression commit changes only the namespace's staleness generations, never its content, and the calculator never holds a namespace preparation across modules. Work: the 2e9 ledger is per preparation; a hit issues no new Work and carries the Work issued by its recorded preparation, whose verdict under the same ledger is unchanged because that preparation is a deterministic function of the key. Signatures: a hit's WAT carries exactly the recorded passive signature segments from ID 0, and its prospective pool and descriptors are the recorded ones, so the engine adopts exactly the keys the original preparation published. The worker separately keeps exact WAT bytes → (the Wasm its selected assembler produced, the compiled `WebAssembly.Module`), matched on the full WAT bytes; a hit skips the assembler re-hash, assembly process and V8 compilation. Instances are never retained, and every module is still instantiated and executed by the guest. Bounds: the host retains at most 96 MiB of accounted bytes (source, types, WAT, prospective compiler state) and each worker at most 64 MiB of WAT plus Wasm bytes, evicting least recently used entries. Neither cache is part of the committed session (see *Committed line and byte-exact restore*): a restore never reads them and never rolls them back. An entry recorded by a module of a failed line was recorded only after that module checked and executed normally, and is the value of a pure function at its full key whether or not the line later committed; a restore only changes the key the next lookup presents. The restored compiler carries the canonical epoch of the last commit (its `text_end`, literal table and generation return together with the arena bytes), so an entry recorded at an epoch the failed line reached matches only when a later line reaches exactly that epoch again. A compiled `WebAssembly.Module` is immutable code without instance state, so one compiled during a failed line is exactly what recompiling the same WAT would produce; the restore removes the failed line's worker artifact files, including its Wasm, and a reused assembly records its content (WAT digest) rather than an earlier stem, which a restore may reissue. `NOBLE_CALCULATOR_MODULE_CACHE=off` disables both. r[CALC-GATE-01] r[CALC-LIMIT-01]

**Rationale:** Most guest modules of a line are repeats: the lexer, parser and display probes recur with identical source and stack types, nearly all boundaries are Program-free, and `text_end` moves only when a new literal content is lowered. Reusing exactly equal checked artifacts removes most of the source-check and backend cost without changing acceptance, identities, caps or the guest's execution of every module; a module the cache has not seen is checked exactly as before. Keying on the namespace recipe rather than a namespace snapshot is exact because namespace construction is a deterministic function of that recipe and later Expression commits never change content. The generation binding moves from the module bytes to the engine's instantiation, but the guard's property is unchanged: a module runs only in an arena whose submission count equals the compiler generation the host validated it against. The measured latency tables, binary hashes and cache on/off comparison are in [the latency record](../../../verification/calculator-v1/latency/README.md).

### Other per-line latency options (#16 1C, 1D, 1E)

**Choice:** Only exact module reuse (above) and the earlier probe-consumer merges are implemented. Environment acceptance reuse (1C: reuse a kernel-checked witness for the committed namespace and check only the new body) is deferred: it changes the kernel acceptance trust root and needs an explicit kernel-trust review that has not been done, and it would not change issued Work. Compiling each named definition once per session (1D) is not adopted: cached Program cells would keep signature IDs alive, so Program-free boundaries — on which both the signature restart and module reuse depend — would become rare, and it only shrinks the backend and worker shares. Coarser guest phases (1E) remain limited to 1A-style merges: the fine split is forced by the 256-node TypeSize and 2e9 per-preparation Work caps, which are not raised. r[CALC-GATE-01]

**Rationale:** 1B removes the repeated source-check and backend work without touching acceptance or identities. 1C is the riskiest trust surface and 1D the largest change, and both lose most of their value once repeats hit the module cache.

### Selected retained-module source boundary

**Choice:** The explicitly selected `ModuleSession::new_calculator` retains at most 524,288 bytes of module source in aggregate. This is a separate profile bound, not an increase to `Limits.bytes`: each new module source/request still has the 262,144-byte candidate limit, and calculator terminal input remains bounded independently at 65,536 bytes. Registration checks the aggregate before parsing or cloning a candidate module. Ordinary and cursor sessions retain their prior aggregate source limit; the selected profile does not relax source checking, node/depth/Work accounting, source-bound identity or opaque nominal identities. r[CALC-BOUND-01] r[CALC-LIMIT-01]

**Rationale:** The eleven separately checked calculator guest modules the shell registers, `result@1` through `calc_defs@1`, now exceed 262,144 bytes together while each remains below the individual source cap. A bounded selected retention allowance admits that real guest closure without inflating caller-supplied limits or granting it to unrelated profiles. This source-retention policy is not a completed calculator scenario or compiled-guest execution claim.

### Guest budget units

**Choice:** Each submitted line builds a fresh guest `num@1.Budget` from the seven CLI values, in slot order `--input-bytes` (0, default 1,024), `--numeric-digits` (1, 256), `--intermediate-bits` (2, 4,096), `--syntax-depth` (3, 32), `--call-depth` (4, 16), `--evaluation-work` (5, 4,000,000) and `--output-size` (6, 4,096). `num@1.budget` refuses a negative slot; the CLI already rejects one. The budget does not carry over between lines. A committed line is never re-evaluated: later lines run on the committed session, and a failed line restores it byte for byte. Every refusal is a guest `ResourceLimit` naming its slot's category. A gate compares before the guarded work runs. A *debit* stores the remaining allowance in the line's Budget; an *admission* only compares and stores nothing. Units:

- **InputBytes:** bytes of the submitted text as framed: an unframed line includes its `\n` terminator (`let x=7` is 8 bytes), and a `--framed` submission is exactly its counted bytes. The same length is the preparse EvaluationWork charge. `expr.preparse_input_*` debits the line's `text.length` once, after the guest lexer has certified the token list and before parsing; it refuses when the length exceeds the allowance. The host's 65,536-byte frame bound (`TransportLimit InputFrameBytes`) is a separate host limit that acts earlier.
- **NumericDigits:** decimal digits of numeric literals, the `.` excluded. `num@1.parse_digit_*` counts each literal's digits and debits them before any width estimate or BigInt is built, so the allowance is shared by all literals of the line. A literal whose count exceeds the remaining allowance refuses.
- **IntermediateIntegerBits:** bits, where width(x) is the bit length of |x| (0 for zero). Gates compare a measured or estimated width W with the allowance and refuse when W exceeds it. All gates are admissions except the power gate, which debits W:
  - A decimal literal of d digits: the estimate w from the Evaluation Work section.
  - A binary operator: width(n1) + width(d1) + width(n2) + width(d2) + 2.
  - Rational normalization: width(num) + width(den) + 2, at the gcd, the numerator finish and the denominator finish.
  - Negation: width(num) + width(den).
  - Power: the projected width W (debited).
  - `to_i64`: width(num). `from_i64`: the bit length of the I64's magnitude, at least 1.
  - Display: width(num) + width(den) + 2, and the width of each finite-decimal digit product.
- **SyntaxDepth:** nesting levels of open parentheses, grouping or call argument list. The parser starts at depth 0. An opening parenthesis is admitted only when depth + 1 ≤ the allowance, and its closing parenthesis returns to the outer depth. The refusal spans the opening parenthesis. The parser keeps the depth itself, so this gate is an admission.
- **CallDepth:** active user-function calls. `num@1.call_enter` debits 1 when a call is entered and refuses if the remaining allowance would become negative. `call_leave` restores the caller's value on return, while the other slots keep the callee's consumption. The top-level expression starts with the full allowance. Defining a function does not evaluate its body and does not charge this slot.
- **EvaluationWork:** the abstract units of the next section. Four charges are not listed there: `from_i64` 250 per bit of that magnitude width, `to_i64` 300 per numerator bit, negation 100·(width(num) + width(den))², and unary plus 1.
- **OutputSize:** bytes of the exact display text, without the newline that the terminal adds. The guest counts them from the canonical Rat before constructing the text, and debits them once. The default display counts a `-` for a negative value, the numerator's decimal digits, and, when the denominator is not 1, `/` plus the denominator's digits. Finite-decimal display counts the sign, the integer digits, and, for f > 0 fraction digits, the point and f digits. A `let` displays its value: this charge runs before the candidate State is published, so a refused display leaves the earlier binding, or its absence, unchanged. After formatting, the host also asserts that the text is at most the budget and 65,536 bytes. A violation is an infrastructure error, never a guest result.

r[CALC-LIMIT-01] r[CALC-STATE-02]

**Rationale:** Each unit is the quantity its guarded loop actually traverses, measured inside the guest from authenticated values, so a bracket N−1/N is deterministic and host-independent. Admissions and debits never approximate: they refuse with `ResourceLimit`. A host timeout, native quota, worker failure or host transport limit is reported under its own label and cannot satisfy or impersonate any of these categories.

### Evaluation Work accounting

**Choice:** `--evaluation-work` (default 4,000,000) is guest Budget slot 5. Every charge is checked quotient-first against the remaining allowance by its own probe before the guarded work runs, and subtracted by its admit. Charges:

- Preparse: 1 per input byte.
- Decimal literal of d digits: estimated width w = ⌊(3322·d + 999)/1000⌋ + 2 = ⌈3.322·d⌉ + 2 for d ≤ 256 (the default NumericDigits budget), else the former 4d + 2. This is at least the bit width of the magnitude and of its 10^f denominator, because 3.322 > log₂10. The literal costs 50·(2w+1)², and w is also the literal's IntermediateIntegerBits estimate.
- Raw rational normalization, with g = width(num) + width(den) + 2: gcd 50·g², numerator finish 25·g², denominator finish 25·g'², where g' = width(reduced num) + width(den) + 2 (`finish_den_measure`), so g' = g when the gcd is 1.
- Power: 100·W² for the projected width W.
- Display: 100·w², where w = width(num) + width(den) + 2.
- Binary operator: 150·C. With a=|n1|, c=|d1|, e=|n2|, f=|d2| and b = a+c+e+f+2, C counts list-element visits of the operator's actual loops. A stepped shift-and-add product with multiplicand width P and multiplier width Q costs M(P,Q) = 4PQ + 2Q² + 9Q + 2. Per operator:
  - × is M(a,e) + M(c,f).
  - ÷ is S = M(a,f) + M(max(c,e), min(c,e)) + c + e + 2.
  - ± is S + M(c,f) + 5b + 9.
  - Every operator adds 2b + 4 for its width measurements.
  - When b exceeds 384, the widths are not packed and C = 8b² + 25b + 19.
  - `op_work_limit` and `op_work_probe` measure the operand widths, and `op_work_route` counts and decides.
- Product roles. The guest loop iterates over the multiplier, so each product's charge follows its stage's operand order:

  | Operator | Product | Stage | Multiplicand | Multiplier | Count |
  |---|---|---|---|---|---|
  | × | n1·n2 | `op_first_stage_seed_mul` | n1 (a) | n2 (e) | M(a,e) |
  | × | d1·d2 | `op_first_stage_second_mul` | d1 (c) | d2 (f) | M(c,f) |
  | ±, ÷ | n1·d2 | `op_first_stage_seed_cross` | n1 (a) | d2 (f) | M(a,f) |
  | ±, ÷ | d1·n2 | `op_first_stage_second_cross` | wider of d1, n2 | narrower; d1 on a tie | M(max(c,e), min(c,e)) + c + e + 2 |
  | ± | d1·d2 | `op_first_stage_sum_den_mul` | d1 (c) | d2 (f) | M(c,f) |

  `op_first_stage_second_cross` measures both widths with `big_width` (c+1 and e+1 positions of `bit_count`, hence c + e + 2) and passes the narrower operand as multiplier. `op_work_probe` orders the same pair the same way, d1 as multiplier on a tie.
- Visit count of M(P,Q). One unit is one position of a guest loop pass. Multiplier bit i (0 ≤ i < Q) sees the multiplicand shifted to width P+i and an accumulator below 2^(P+i), so their sum has at most P+i+1 positions. Each bit costs 7 fixed units: route, probe and shift, plus the add's begin and the terminal steps of its continue, trim and reverse passes. A set bit's add also costs 4(P+i+1): digit, continue, trim and reverse over each sum position. Summed over the Q bits, this is 4PQ + 2Q(Q−1) + 4Q + 7Q = 4PQ + 2Q² + 9Q, and the cursor start and the final route on the empty multiplier add 2. The Q² term follows the multiplier: with d1 = 1, the former d1·n2 order cost M(1,e) = 2e² + 13e + 2, and the width-ordered stage costs M(e,1) + e + 3 = 5e + 16.
- Above-384-bit bound. With s = a+c+e+f = b−2 and Q* = min(c,e), so that Q*² ≤ ce:
  - ± is 4(af + ce + cf) + 2Q*² + 4f² + 18f + 9Q* + c + e + 7b + 21.
  - Its quadratic terms are at most 4s², because 4s² ≥ 4f² + 8af + 8ce + 8cf. Its linear terms 18f + 9Q* + c + e are at most 18s. So C(±) ≤ 4s² + 18s + 7b + 21 = 4b² + 9b + 1.
  - ÷ is ± without M(c,f) + 5b + 9, so it is smaller.
  - × is 4ae + 2e² + 4cf + 2f² + 9e + 9f + 2b + 8 ≤ 4s² + 9s + 2b + 8 = 4b² − 5b + 6.
  - Every kind is therefore below 8b² + 25b + 19, and the landed cap stays a sound bound. Its value is unchanged, so admission above 384 bits does not change.

r[CALC-LIMIT-01]

**Rationale:** Each charge is at least the number of guest list-element visits of the work it admits, so admission bounds work deterministically before it runs. The former operator charge, 150·b², charged integer addition as a full multiplication. It also undercounted lopsided products, because the guest shift-and-add iterates over the multiplier and pays a Q² term. The ± and ÷ cross product d1·n2 formerly took n2 as multiplier. Integer ± and ÷ (d1 = 1) therefore paid 2e² in Work and one stepped stage per bit of n2, plus an add for each set bit. The width-ordered stage pays M(max, min) plus the c + e + 2 width count. That is never more than either fixed order plus at most b units, and it adds no guest submission. A fixed swap (d1 always the multiplier) would instead move the Q² term onto d1, and decimal and rational left operands have wide denominators. The tighter forms keep the 4,000,000 default: two 16-digit integer operands no longer exhaust it. Runtime quotas (steps, allocation, session cells) depend only on the widths a submission touches. Every value of width X still requires a gate costing at least 100·X², through power, literal or normalization. Operator submissions above 384 bits pay at least 150·b². So the largest width an admitted line can touch is at most max(384, the former frontier) for the same budget, and no new runtime-quota exposure is introduced. A denial remains a deterministic `ResourceLimit EvaluationWork`, never a host timeout.

### Host stack protocol

**Choice:** Every host stage is a separately compiled guest module typed over the whole retained operand stack, so the shell arranges that stack to keep each compile under the selected caps. The cost model, from the compiler:

- *Quotation concretization.* A quotation's row variables are instantiated to the concrete stack beneath it. `dip : S a Program<S,T,e> -- T a ! e` therefore types its quotation as `Program<S,T>` over every cell below the one held item, and preflight counts that whole type against the request's `type_size` of 256 structural nodes per instantiated stack entry or value binding (`concrete::count`). A `Program` counts 1 plus every node of its input and output rows: a quotation pays for everything beneath it, once on each side.
- *`dip` excludes exactly one item.* Only the top cell is outside the quotation's type; every deeper cell is inside it.
- *Generic nominals count twice.* `type_children` walks both the arguments and the substituted descriptor of a generic nominal, so `Result<A,B>` counts 1 + 2|A| + 2|B|. A builtin `Sum<A,B>` or `Pair<A,B>` counts 1 + |A| + |B|.
- *Work scales with the environment.* Preflight prices every node against the concrete frame beneath it, including each nominal lookup times the environment's nominal and generic-variant rows. Admission then grants an allowance of `environment_work × (named + 3)` and spends it on one whole-environment scan, the named schemes and one independent kernel environment validation per body. Every environment row therefore raises the cost of every stage, and every named body in a stage's closure raises it by a further `environment_work`. All of it shares the 2,000,000,000-unit issued ceiling per preparation.

The rules the host follows where a stage is near a cap:

- *Register on top, stage under `dip`.* Move the large context (State, display flag, `FrameHot`) into one cell on top and run the stage as `[ stage ] dip`, so the stage's quotation types over its small operands only. `swap [ stage ] dip swap` is the same rule when the context sits second.
- *Stage wrapper rule.* A wrapped stage W must satisfy 1 + |W_in| + |W_out| ≤ 256, where |W_in| and |W_out| are the node totals of the cells below the held one before and after; inside it, every quotation obeys the same bound over its own concrete stack.
- *Park large values above heavy callees.* When the cells a callee must not see do not fit in one held item, pair them and hold the pair: `[ pair ] dip swap [ X ] dip swap [ unpair ] dip`. When the callee's closure is near the Work ceiling, park, run and unpark in separate compiles, so no single preparation types the callee's nodes over the State-carrying cells.
- *Prefer builtin sums for large payloads.* Carry a large Pending/cursor pair in `Sum<_,Unit>` (`inl`/`inr`) while it is large and convert back to `Result` once it is small (`TO_SUM`/`FROM_SUM`).

The layout `main` actually uses:

- *Lexing* runs top-level words over `[ State Bool Text cursor… ]` with no `dip`; the finite-decimal flag and source arrive above State.
- *Parsing* uses `phase()`, `[ swap ] dip swap [ w ] dip swap [ swap ] dip`, which hides the third cell of `[ hidden Bool Parser ]`. The hidden cell is State, `Pair<State,Name>` for a let, or State paired with function metadata.
- *Evaluation* runs over `[ Ctx FrameHot ]`, then `[ Ctx carrier ]`, with `Ctx = Pair<State,Bool>` or, for a let, `Pair<Pair<State,Bool>,Result<Name,Unit>>`. The numeric stage macros (`eval_stage!`, `span_stage!`, `sum_*`) hide Ctx with `swap [ … ] dip swap`; literal and binary-operator stages hide two cells. Heavy numeric, GCD, finish and parser-fault stages use the pair-parked form. `count_finite_round` and the ASCII fraction finish park, run and restore in separate compiles.
- *Calls* never park the caller frame on the typed stack. During a callee the worker holds exactly `[ Ctx FrameHot ]`. The guest stashes the caller Text and remaining tokens in a State-held function frame and restores the exact caller State when the body completes. Call stages type over `[ Reg Carrier ]` with `Reg = Pair<Ctx,FrameHot>` second, and push status above it with `calc_bits@1.rot`.
- *Display* stages over `Bool Pair<State,X>` and the parked `Pair<State,Bool>`. The ASCII bit scan keeps State on top and runs its stages under `dip`.
- *Status* is read from the top cell (`stack.last()`), then consumed by a quotation-free `drop` or `unpair drop` prefixed to the next module. The exceptions are variable lookup, which reads its probe under the register (second cell), and the power-loop probe, which reads `[ carrier Bool Ctx ]`.

An unpublished pre-port draft stated invariants I1–I5: one register on top; stages run as `[ stage ] dip` under the wrapper rule and an inner rule 1 + |below| + |consumed| + |out| ≤ 256; quotation-free register moves; no large values beneath a quotation; status read from the working top (`stack[len-2]`). `main` departs from it:

- I1 holds only for variable lookup, the power-loop probe and the ASCII bit scan. Arithmetic keeps Ctx second, the call path keeps its register second, parsing hides the third cell, and display keeps State inside the top pair.
- I2 holds in substance through `swap [ … ] dip swap`, the double-hiding `span_stage!` and `phase()`. Top-level frame words such as `frame_hot_failed` and `frame_peek_kind` run with no `dip` over `[ Ctx FrameHot ]`.
- I3 is not followed. `phase()`, the stage macros and the call path move cells with quotations (`[ swap ] dip`, `calc_bits@1.rot`).
- I4 is applied selectively, by parking, splitting and builtin sums, where a measured stage crossed a cap. It is not a global invariant.
- I5 applies only to the two probes above. Every other status read takes the top cell.

The calculator headroom check (`tools/calculator-headroom.mjs`) reports each stage's distance from every cap on real stage chains. A rewrite to the full draft is warranted only where that report shows a stage under its margin.

**Rationale:** The type-size and Work caps are per preparation, and every stage is its own preparation, so the cost of a stage is set by the stack it is typed over, not by the work it does. Keeping these rules only in host comments let later additions of nominals or environment rows push formatter and evaluator words over a cap without warning. Recording the cost model, the rules and the actual layout lets a change predict which stages it affects; the headroom check measures the result. r[CALC-LIMIT-01]

### Compile-cost headroom

**Choice:** Every calculator preparation exposes its own accounting (`Prepared::metrics()`: issued Work and its preflight, environment and plan grants, environment rows and per-scan work, named bodies, the largest admitted instantiated type, signature keys and retained-key charge, table end, `text_end`, WAT bytes) beside the code's caps (`CALCULATOR_CAPS`). The opt-in calculator trace carries them as each module record's `compile` object. `tools/calculator-headroom.mjs run` drives the real host stage chains over a fixed vector set (`1+2`, `1 2`, `fn f(y)=y*2` then `f(3)`, `2^10`, `1/8` with `--finite-decimal`, `22/7`; a six-line definition session on request) and reports each cap's lowest headroom and the stage that set it. Margins are configurable; by default Work headroom under 100,000,000 fails and the other caps warn. Being hours long, the run is a gate, not a default test; `tools/calculator-headroom.test.mjs` tests the margin logic. Its first output (`verification/calculator-headroom/first-output.txt`, all six vectors, 3,641 compiles, before the call-stage splits below) failed the Work margin: the call-entry stash stage `[ unpair ] dip swap [ [ unpair ] dip swap [ expr.call_enter_stash_guest ] dip swap [ pair ] dip ] dip swap [ pair ] dip` of `f(3)` (803 rows, 17 named) issued 1,931,536,742 units, 68,463,258 below the cap. It also warned that `[ expr.preparse_quota_fault ] dip` admits a 256/256 type. The tightest rows compile uses 820 of 896 rows, and no compile uses more than 34 of 512 named bodies.

*Environment admission.* Measured over the 3,641 compiles: one environment scan costs 15.76M–16.50M Work at 786–820 rows (about 20,000 per row), and the `environment_work × (named + 3)` allowance is 11.3% of all issued Work. Each added row therefore costs every stage about 20,000 × (named + 3). An experimental build changed only the accounting: one `environment_work` kernel charge per preparation and an allowance of `environment_work × 3`, as if every body's kernel check reused one environment validation. Not adopted. Paired by module with the final build on all six vectors (3,641 compiles, identical module sources), it saves exactly `environment_work × named` in every compile: median 31.7M, at most 549.6M, 6.6% of issued Work; its lowest Work headroom over every compile would be 310.7M. In the failing call-entry stage it saves 275,539,179, which would raise its headroom from 68.5M to 344.0M. Options:

- Keep the per-body allowance and split the stages under the margin (chosen, done). The guest word `call_enter_stash_guest` became `call_enter_stash_prep_guest` and `call_enter_stash_push_guest`, compiled separately over the same `[ Reg Carrier ]` layout (68.5M → 730.2M and 339.6M). Splitting it exposed two more call stages under the margin. `call_scan_resolve_guest` became `call_scan_search_guest` (variable search) and `call_scan_resolve_guest` (its Result) (80.0M → 305.3M and 929.4M). The lookup tick's `calc_bits@1.rot calc_bits@1.rot` moved into its own compile (98.5M → 242.0M; 1,256.0M for the move). An inline `swap [ swap ] dip` was tried instead and refused by the source checker, because its quotation types over the register past the TypeSize bound; the named `rot` body is checked generically and stays under it. Guest results are unchanged: `f(3)` still prints `6`.
- Validate the environment once per preparation and let every body's kernel check reuse it. This is the measured saving above, and it would lift every stage. It needs a kernel API that ties each body check to the one validated environment, which is a trusted-kernel change needing its own review.
- Reuse environment acceptance across preparations (#16 option 1C). #16 defers it; its artifact reuse (1B) changes latency, not issued Work.

After the splits every traced compile of `f(3)` and `1+2` is at least 143.3M below the Work cap (`call_body_finish_guest` is now the tightest call stage), recorded in `verification/calculator-headroom/second-output.txt`; the first output is kept as the pre-split baseline. Split further stages when the check fails again. The second option is the structural fix if splits stop sufficing.

*Monotonic compiler state.* Static literal Text is never rewound, because live data Text may name static addresses. A calculator compiler content-addresses it instead: an exact literal byte string keeps the address it was first given (`static_literals`), and every module that lowers it still initializes those same bytes there through its own segment. An address therefore only ever holds one content, so a cell from an earlier module keeps reading it, and `text_end` grows only with the distinct literal contents ever compiled, not with lines, sessions or modules. Host stage sources contain no Text literals and user input reaches the guest only as injected Text, so those contents are the guest modules' own literals, `"let"` and `"fn"` today: `text_end` stays within 5 of its 458,752 bytes for the whole life of a session, with or without a replay or line limit. Before content addressing, every identifier-led line advanced it 5 bytes (measured), which a long-lived session would eventually exhaust. The retained-key charge of each preparation is the expanded length of the retained pool, which the pool refuses above 4,194,304 bytes, so it is at most 4,194,304 Work, under 5% of the 100M margin. Measured: 0 in every traced compile, because every boundary after a session's first module was Program-free and restarted the pool. Both stay bounded with the caps unchanged.

**Rationale:** Stage rewrites were forced by caps that nothing reported. Exposing the compiler's own numbers and checking them on real chains turns the next overrun into a warning with a named stage. r[CALC-LIMIT-01]

## Risks and boundaries

- Bounded selected memory is not a general garbage collector. Only at a Calculator-v1 submission boundary, before `begin`, while no continuation is live (`cp = 0`), the runtime's own `collect` export compacts the cells reachable from the operand stack. This is the selected backend runtime, not the shell or candidate code, and it issues no host request. Survivors keep their relative handle order, so every `a`/`b`/`c` edge stays strictly backward. Live dynamic Text slides with its cell. The vacated cell tail, freed Text bytes, the per-submission type-certificate table and observation globals are zeroed. A stale handle above the new cursor therefore fails liveness. Reclamation is safe because no calculator handle survives outside the worker's operand stack: the shell injects only Text/I64/Bool, never reads report handles, and Calculator-v1 refuses `park` and `project`. Compiled bodies keep quotation and callee handles in instance-private globals, so a boundary where any reachable Program runs compiled code (table entry ≥ 5) moves nothing. A malformed root, edge or Text order fails closed and terminates the session. Handles are therefore valid only until the next execute; never retain one across submissions. The 72,362-cell, 64-page and per-submission allocation caps are unchanged. Implementation choice under S-MEM-04; ordinary, cursor, declared and LIVE profiles still never reclaim.
- The shared 16,384-entry function table is reused, never enlarged. Every calculator module re-lowers its own named-definition closure, and its compiled bodies read Program handles only from instance-private globals, so an earlier module's compiled slots are reachable only through a live Program cell whose table entry is at least 5. After a normal submission the runtime's read-only `compiled_programs_reachable` export runs the `collect` mark closure; a live continuation, failure or malformed arena answers reachable. When nothing is reachable, the next preparation restarts its function allocation at base 5 and its `$initialize` `table.init` overwrites only dead slots; the core entries 0..4 are never rewritten. Otherwise allocation continues above every committed slot. Host pushes between submissions are Text, I64 or Bool and cannot introduce a Program. The same quiescent preparation restarts the definition-identity ledger empty: identities are session-stable ids checked against their recipes, plan and emission never read the ledger, and no earlier epoch's compiled body can run again, so each epoch admits at most 512 distinct identities while ordinary preparations still retain and check the whole ledger.
- The 8,192-key signature pool restarts only at a stricter, Program-free boundary. After a normal submission whose `compiled_programs_reachable` answer is 0, the runtime's read-only `programs_reachable` export runs the same `collect` mark closure and answers 1 if any marked cell is a Program (kind 4), recipe atom or concatenation (8, 9) or Syntax (10), or if the arena is malformed or failed; the engine reports both answers and the host refuses a report where a compiled Program is reachable but no Program is. Signature IDs are held at runtime only by those cells: Program interfaces, literal schemas and invocation witnesses in recipe atoms, and certified cells (16) that copy the interface of the Program they reference through a followed child, so a reachable certified cell implies a reachable Program. No other runtime structure carries an ID across a boundary: `$observed_program` and the recipe cursors are instance-private and also cleared by `collect`, which runs before every Calculator-v1 submission and zeroes the shared certificate page, and the host pushes only Text, I64 and Bool. On the compiler side the definition-identity ledger, whose recipes may name signatures, already restarts at every quiescent boundary, which a Program-free one implies, and earlier modules' compiled code is dead by the table-reuse argument. At such a boundary `prepare_program_free` starts the meter and the prospective pool from a fresh calculator pool, empties the published descriptors in the same epoch, and publishes from descriptor 0. The engine's `recordSignatures` keeps only `signatures.slice(0, first)` and refills `[first, end)`, so `first = 0` replaces the whole table, and `readSignature` bounds-checks every ID against it. Transaction provenance compares only the retained signature and descriptor prefixes, which are empty after a restart, and the key limit still applies within each epoch. Static literal Text and `text_end` are never rewound because live data Text may name static addresses; literals are content-addressed instead, so neither `text_end` nor the retained-key charge can approach its cap (see *Compile-cost headroom*). Ordinary-profile WAT is byte-identical.
- Each committed line costs one 4 MiB arena copy in the worker and one host copy of the namespace and compiler, and a restore also deletes the failed line's scratch artifacts. Nothing reconstructs a session from history: a failed restore verification, or a dead or timed-out worker, ends it. Because the arena starts at 64 pages, the runtime `memory_bytes` metric always reports 4 MiB. A restore does not expand a guest `EvaluationWork` budget or make a failed line successful.
- Complete CALC conformance, independent numeric oracle/negative controls, AI-authoring benchmark and actual-Rust formal refinement require separate evidence. No result of those gates is claimed here.
