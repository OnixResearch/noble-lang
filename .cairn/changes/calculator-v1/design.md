# Calculator-v1 selected guest design

## Context and scope

The accepted CALC requirements describe an application, not a new language conformance profile. This active design selects a separate `noble calculator` route after M4 and the library/module/text/iteration/error-schema gates. Core-Bootstrap keeps wrapping `I64`; ordinary, cursor, declared-module and LIVE environments do not inherit calculator builtins, memory expansion or preparation allowances. No canonical calculator scenario is promoted by this design. r[CALC-SCOPE-01] r[CALC-GATE-01]

## Decisions

### Pure typed guest, narrow terminal shell

**Choice:** Install checked Noble modules for lexical input, exact numbers, rational normalization, parser/evaluator state, diagnostics and display. Every operation of a line is a freshly checked Noble source submission compiled by the selected Wasm backend. The shell may frame bytes, supply seven nonnegative guest budgets, schedule a guest-certified action kind, observe a bounded typed result and retain accepted line sources. It must not parse an expression, resolve a name, calculate a rational, choose an exact display representation, inspect an opaque guest state, supply filesystem/network/clock/process imports, or convert a native error into a guest result. All guest phases of one candidate line share the same checked ModuleSession, prospective compiler and Wasm worker; their state remains on the guest typed stack. r[CALC-SCOPE-01] r[CALC-BOUND-01]

**Rationale:** A host-only evaluator, separately instantiated one-step stand-ins and host reinjection of private parser/numeric state would satisfy neither the compiled Noble backend nor transactional application contract. Phase boundaries are an implementation device, not a second trust boundary or a reset of an individual compiler preparation's accounting. r[CALC-GATE-01]

### Tentative line and replay boundary

**Choice:** Before interpreting a new line, enforce bounded accepted-command count, retained source bytes and replay effort as explicit host limits. Construct a fresh *candidate* worker from independently checked modules and replay only previously accepted lines in source order. Run all typed phases of the new line in that one candidate worker. Publish its new compiler, worker, typed state and accepted source only after guest acceptance and budgeted exact formatting succeed; otherwise discard it and keep the prior accepted session. A later terminal submission may use a different fresh worker and replay the accepted history. Terminal write failure after a successful commit does not undo that commit. r[CALC-STATE-02]

**Rationale:** A native quota or trap can poison the candidate's Wasm handles. Replaying accepted input into an isolated candidate prevents a failed line from mutating or invalidating the prior worker; explicit replay bounds prevent indefinite reconstruction. Host transport/history limits are labeled separately from the seven guest `ResourceLimit` categories. r[CALC-STATE-02] r[CALC-LIMIT-01]

### Independent selected compiler and memory bounds

**Choice:** The selected source compiler checks borrowed structure, concrete substitutions, complete definition/environment closure, each independent kernel acceptance and identity before publishing a compiler state. It separately bounds 512 reachable named bodies and 896 environment rows, including derived nominal operations; every reachable row retains independent kernel replay. Only during calculator borrowed preflight, before any owned kernel witness clone, each nonzero `Work::charge(amount)` first grants exactly that measured amount through the checked calculator ledger. This preserves the request's original preparation allowance (currently at most 512,000,000 units) for admission and kernel acceptance. The borrowed-preflight grant scope ends before admission; it does not mark the whole submission trusted or enable plan grants across kernel clones. The existing finite environment-work allowance follows environment validation, and only after independent kernel acceptance and identity may plan lowering issue measured shortfalls. All grants and the original allowance share one cumulative ceiling of 2,000,000,000 issued units per preparation. These units bound charged structural operations, **not** a physical CPU/time guarantee. Separate per-type, stack, source, signature and emission caps still reject submissions without raising the work cap. The calculator-only managed runtime imports 16 initial pages and at most 64 pages; at most 72,362 48-byte cell handles fill its disjoint regions up to the exclusive 4 MiB end. Within a submission handles are retained monotonically; only the order-preserving boundary compaction under *Risks and boundaries* reclaims cells, and a handle is valid only until the next submission. The per-invocation allocation limit remains 1,376,208 bytes; no expanded ordinary memory is implied. Text and transient signature-observation scratch stay distinct and observed signatures are copied before scratch reuse. Ordinary and cursor memory remain at their established 16-page maximum. r[CALC-BOUND-01] r[CALC-LIMIT-01] r[CALC-GATE-01]

**Rationale:** Forged direct submissions and deeply expanded type witnesses must not bypass independent checking or disguise physical preclone work; calculator's larger exact-number closure cannot consume ordinary profile authority or memory. Borrowed per-appearance and named-body scans are charged cumulatively; only the exceptional first stack mismatch is reserved once, against the maximum of each actual join's frame/input pair and each root, named or quotation completion's frame/claimed-output pair, never against unrelated frames or heights. A selected backend exhaustion, assembly refusal, engine trap, timeout or host replay bound is never relabeled as deterministic guest `ResourceLimit`. r[CALC-LIMIT-01]

### Selected retained-module source boundary

**Choice:** The explicitly selected `ModuleSession::new_calculator` retains at most 524,288 bytes of module source in aggregate. This is a separate profile bound, not an increase to `Limits.bytes`: each new module source/request still has the 262,144-byte candidate limit, and calculator terminal input remains bounded independently at 65,536 bytes. Registration checks the aggregate before parsing or cloning a candidate module. Ordinary and cursor sessions retain their prior aggregate source limit; the selected profile does not relax source checking, node/depth/Work accounting, source-bound identity or opaque nominal identities. r[CALC-BOUND-01] r[CALC-LIMIT-01]

**Rationale:** The eleven separately checked calculator guest modules the shell registers, `result@1` through `calc_defs@1`, now exceed 262,144 bytes together while each remains below the individual source cap. A bounded selected retention allowance admits that real guest closure without inflating caller-supplied limits or granting it to unrelated profiles. This source-retention policy is not a completed calculator scenario or compiled-guest execution claim.

### Evaluation Work accounting

**Choice:** `--evaluation-work` (default 4,000,000) is guest Budget slot 5. Every charge is checked quotient-first against the remaining allowance by its own probe before the guarded work runs, and subtracted by its admit. Charges:

- Preparse: 1 per input byte.
- Decimal literal of d digits: estimated width w = ⌊(3322·d + 999)/1000⌋ + 2 = ⌈3.322·d⌉ + 2 for d ≤ 256 (the default NumericDigits budget), else the former 4d + 2. This is at least the bit width of the magnitude and of its 10^f denominator, because 3.322 > log₂10. The literal costs 50·(2w+1)², and w is also the literal's IntermediateIntegerBits estimate.
- Raw rational normalization, with g = width(num) + width(den) + 2: gcd 50·g², numerator finish 25·g², denominator finish 25·g².
- Power: 100·W² for the projected width W.
- Display: 100·w², where w = width(num) + width(den) + 2.
- Binary operator: 150·C. With a=|n1|, c=|d1|, e=|n2|, f=|d2| and b = a+c+e+f+2, C counts list-element visits of the operator's actual loops. A stepped shift-and-add product with multiplicand width P and multiplier width Q costs M(P,Q) = 4PQ + 2Q² + 9Q + 2. Per operator:
  - × is M(a,e) + M(c,f).
  - ÷ is M(a,f) + M(c,e).
  - ± is M(a,f) + M(c,e) + M(c,f) + 5b + 9.
  - Every operator adds 2b + 4 for its width measurements.
  - When b exceeds 384, the widths are not packed and C = 8b² + 25b + 19.
  - `op_work_limit` and `op_work_probe` measure the operand widths, and `op_work_route` counts and decides.

r[CALC-LIMIT-01]

**Rationale:** Each charge is at least the number of guest list-element visits of the work it admits, so admission bounds work deterministically before it runs. The former operator charge, 150·b², charged integer addition as a full multiplication. It also undercounted lopsided products, because the guest shift-and-add iterates over the multiplier and pays a Q² term. The former literal width 4d+2 overestimated bits by about 20%, and that overestimate was squared. The tighter forms keep the 4,000,000 default: two 16-digit integer operands no longer exhaust it. Runtime quotas (steps, allocation, session cells) depend only on the widths a submission touches. Every value of width X still requires a gate costing at least 100·X², through power, literal or normalization. Operator submissions above 384 bits pay at least 150·b². So the largest width an admitted line can touch is at most max(384, the former frontier) for the same budget, and no new runtime-quota exposure is introduced. A denial remains a deterministic `ResourceLimit EvaluationWork`, never a host timeout.

### Host stack protocol

**Choice:** Every host stage is a separately compiled guest module typed over the whole retained operand stack, so the shell arranges that stack to keep each compile under the selected caps. The cost model, from the compiler:

- *Quotation concretization.* A quotation's row variables are instantiated to the concrete stack beneath it. `dip : S a Program<S,T,e> -- T a ! e` therefore types its quotation as `Program<S,T>` over every cell below the one held item, and preflight counts that whole type against the request's `type_size` of 256 structural nodes per instantiated stack entry or value binding (`concrete::count`). A `Program` counts 1 plus every node of its input and output rows: a quotation pays for everything beneath it, once on each side.
- *`dip` excludes exactly one item.* Only the top cell is outside the quotation's type; every deeper cell is inside it.
- *Generic nominals count twice.* `type_children` walks both the arguments and the substituted descriptor of a generic nominal, so `Result<A,B>` counts 1 + 2|A| + 2|B|. A builtin `Sum<A,B>` or `Pair<A,B>` counts 1 + |A| + |B|.
- *Work scales with the environment.* Preflight prices every node against the concrete frame beneath it, including each nominal lookup times the environment's nominal and generic-variant rows. Admission then grants an allowance of `environment_work × (named + 3)` and spends it on one whole-environment scan, the named schemes and one independent kernel environment validation per body. Every environment row therefore raises the cost of every stage, and every named body in a stage's closure raises it by a further `environment_work`. All of it shares the 2,000,000,000-unit issued ceiling per preparation.

The rules the host follows where a stage is near a cap:

- *Register on top, stage under `dip`.* Move the large context (State, display flag, `FrameHot`) into one cell on top and run the stage as `[ stage ] dip`, so the stage's quotation types over its small operands only. `swap [ stage ] dip swap` is the same rule when the context sits second.
- *Stage wrapper rule.* A wrapped stage W must satisfy 1 + |W_in| + |W_out| ≤ 256, where |W_in| and |W_out| are the node totals of the cells below the held one before and after; inside it, every quotation obeys the same bound over its own concrete stack.
- *Park large values above heavy callees.* When the cells a callee must not see do not fit in one held item, pair them and hold the pair: `[ pair ] dip swap [ X ] dip swap [ unpair ] dip`. When the callee's closure is near the Work ceiling, park, run and unpark in separate compiles, so no single preparation types the callee's nodes over the State-carrying cells.
- *Prefer builtin sums for large payloads.* Carry a large Pending/cursor pair in `Sum<_,Unit>` (`inl`/`inr`) while it is large and convert back to `Result` once it is small (`TO_SUM`/`FROM_SUM`).

The layout `main` actually uses:

- *Lexing* runs top-level words over `[ State Bool Text cursor… ]` with no `dip`; the finite-decimal flag and source arrive above State.
- *Parsing* uses `phase()`, `[ swap ] dip swap [ w ] dip swap [ swap ] dip`, which hides the third cell of `[ hidden Bool Parser ]`. The hidden cell is State, `Pair<State,Name>` for a let, or State paired with function metadata.
- *Evaluation* runs over `[ Ctx FrameHot ]`, then `[ Ctx carrier ]`, with `Ctx = Pair<State,Bool>` or, for a let, `Pair<Pair<State,Bool>,Result<Name,Unit>>`. The numeric stage macros (`eval_stage!`, `span_stage!`, `sum_*`) hide Ctx with `swap [ … ] dip swap`; literal and binary-operator stages hide two cells. Heavy numeric, GCD, finish and parser-fault stages use the pair-parked form. `count_finite_round` and the ASCII fraction finish park, run and restore in separate compiles.
- *Calls* never park the caller frame on the typed stack. During a callee the worker holds exactly `[ Ctx FrameHot ]`. The guest stashes the caller Text and remaining tokens in a State-held function frame and restores the exact caller State when the body completes. Call stages type over `[ Reg Carrier ]` with `Reg = Pair<Ctx,FrameHot>` second, and push status above it with `calc_bits@1.rot`.
- *Display* stages over `Bool Pair<State,X>` and the parked `Pair<State,Bool>`. The ASCII bit scan keeps State on top and runs its stages under `dip`.
- *Status* is read from the top cell (`stack.last()`), then consumed by a quotation-free `drop` or `unpair drop` prefixed to the next module. The exceptions are variable lookup, which reads its probe under the register (second cell), and the power-loop probe, which reads `[ carrier Bool Ctx ]`.

An unpublished pre-port draft stated invariants I1–I5: one register on top; stages run as `[ stage ] dip` under the wrapper rule and an inner rule 1 + |below| + |consumed| + |out| ≤ 256; quotation-free register moves; no large values beneath a quotation; status read from the working top (`stack[len-2]`). `main` departs from it:

- I1 holds only for variable lookup, the power-loop probe and the ASCII bit scan. Arithmetic keeps Ctx second, the call path keeps its register second, parsing hides the third cell, and display keeps State inside the top pair.
- I2 holds in substance through `swap [ … ] dip swap`, the double-hiding `span_stage!` and `phase()`. Top-level frame words such as `frame_hot_failed` and `frame_peek_kind` run with no `dip` over `[ Ctx FrameHot ]`.
- I3 is not followed. `phase()`, the stage macros and the call path move cells with quotations (`[ swap ] dip`, `calc_bits@1.rot`).
- I4 is applied selectively, by parking, splitting and builtin sums, where a measured stage crossed a cap. It is not a global invariant.
- I5 applies only to the two probes above. Every other status read takes the top cell.

The calculator headroom check (`tools/calculator-headroom.mjs`) reports each stage's distance from every cap on real stage chains. A rewrite to the full draft is warranted only where that report shows a stage under its margin.

**Rationale:** The type-size and Work caps are per preparation, and every stage is its own preparation, so the cost of a stage is set by the stack it is typed over, not by the work it does. Keeping these rules only in host comments let later additions of nominals or environment rows push formatter and evaluator words over a cap without warning. Recording the cost model, the rules and the actual layout lets a change predict which stages it affects; the headroom check measures the result. r[CALC-LIMIT-01]

### Compile-cost headroom

**Choice:** Every calculator preparation exposes its own accounting (`Prepared::metrics()`: issued Work and its preflight, environment and plan grants, environment rows and per-scan work, named bodies, the largest admitted instantiated type, signature keys and retained-key charge, table end, `text_end`, WAT bytes) beside the code's caps (`CALCULATOR_CAPS`). The opt-in calculator trace carries them as each module record's `compile` object. `tools/calculator-headroom.mjs run` drives the real host stage chains over a fixed vector set (`1+2`, `1 2`, `fn f(y)=y*2` then `f(3)`, `2^10`, `1/8` with `--finite-decimal`, `22/7`; a six-line definition session on request) and reports each cap's lowest headroom and the stage that set it. Margins are configurable; by default Work headroom under 100,000,000 fails and the other caps warn. Being hours long, the run is a gate, not a default test; `tools/calculator-headroom.test.mjs` tests the margin logic. Its first output is `verification/calculator-headroom/first-output.txt`: lowest Work headroom 234,454,196 (`op_work_probe`, 793 rows, 7 named), TypeSize 256/256 at `[ expr.preparse_quota_fault ] dip` (a warning), 814 of 896 rows, at most 28 of 512 named bodies.

*Environment admission.* Measured over 1,051 compiles: one environment scan costs 15.76M–16.50M Work at 786–814 rows (about 20,000 per row), and the `environment_work × (named + 3)` allowance is 11.3% of all issued Work. Each added row therefore costs every stage about 20,000 × (named + 3). In the tightest compile the allowance is 159,334,050, of which the per-body kernel environment validations are 111,533,835. Options:

- Keep the per-body allowance (chosen). The measured minimum headroom exceeds the 100M margin by 134M, and the check fails before a stage crosses it.
- Validate the environment once per preparation and let every body's kernel check reuse it. That would remove at most `environment_work × named` from each stage (≤111.5M in the tightest compile; computed from the measured components, not yet from an experimental build). It needs a kernel API that ties each body check to the one validated environment, a trusted-kernel change that needs its own review.
- Reuse environment acceptance across preparations (#16 option 1C). #16 defers it; its artifact reuse (1B) changes latency, not issued Work.

Revisit the second option when the report shows a stage under its Work margin.

*Monotonic compiler state.* Static literal Text grows by the bytes of each literal occurrence a module lowers. The guest's only Text literals are `"let"` and `"fn"` in `header_let_pair` and `header_fn_pair`, which the host runs once each per line that starts with an identifier; host stage sources have none. A candidate session runs at most 64 lines (`HISTORY_COMMANDS_LIMIT`), so `text_end` advances at most 320 of its 458,752 bytes. Measured: 5 bytes per executed line in a six-line session with three replayed definitions. The retained-key charge of each preparation is the expanded length of the retained pool, which the pool refuses above 4,194,304 bytes, so it is at most 4,194,304 Work, under 5% of the 100M margin. Measured: 0 in every traced compile, because every boundary after a candidate's first module was Program-free and restarted the pool. Neither is rewound; both stay bounded with the caps unchanged.

**Rationale:** Stage rewrites were forced by caps that nothing reported. Exposing the compiler's own numbers and checking them on real chains turns the next overrun into a warning with a named stage. r[CALC-LIMIT-01]

### Evidence and lifecycle

**Choice:** Exercise full compiled guest paths and negative controls separately from document validation. Preserve canonical CALC-01 through CALC-13 states and older M1–M4 evidence. Do not infer an accepted case from one arithmetic vector, a source typecheck, successful WAT assembly, a local native delta or proof about wrapping `I64`. This package remains active/unselected until its source and actual guest observations meet their gates. Pinned Cairn lifecycle gates are unrun under the current explicit no-Nix/low-space directive; offline local specification checks, if run, cannot substitute for them. r[CALC-GATE-01]

## Risks and boundaries

- Bounded selected memory is not a general garbage collector. Only at a Calculator-v1 submission boundary, before `begin`, while no continuation is live (`cp = 0`), the runtime's own `collect` export compacts the cells reachable from the operand stack. This is the selected backend runtime, not the shell or candidate code, and it issues no host request. Survivors keep their relative handle order, so every `a`/`b`/`c` edge stays strictly backward. Live dynamic Text slides with its cell. The vacated cell tail, freed Text bytes, the per-submission type-certificate table and observation globals are zeroed. A stale handle above the new cursor therefore fails liveness. Reclamation is safe because no calculator handle survives outside the worker's operand stack: the shell injects only Text/I64/Bool, never reads report handles, and Calculator-v1 refuses `park` and `project`. Compiled bodies keep quotation and callee handles in instance-private globals, so a boundary where any reachable Program runs compiled code (table entry ≥ 5) moves nothing. A malformed root, edge or Text order fails closed and terminates the session. Handles are therefore valid only until the next execute; never retain one across submissions. The 72,362-cell, 64-page and per-submission allocation caps are unchanged. Implementation choice under S-MEM-04; ordinary, cursor, declared and LIVE profiles still never reclaim.
- The shared 16,384-entry function table is reused, never enlarged. Every calculator module re-lowers its own named-definition closure, and its compiled bodies read Program handles only from instance-private globals, so an earlier module's compiled slots are reachable only through a live Program cell whose table entry is at least 5. After a normal submission the runtime's read-only `compiled_programs_reachable` export runs the `collect` mark closure; a live continuation, failure or malformed arena answers reachable. When nothing is reachable, the next preparation restarts its function allocation at base 5 and its `$initialize` `table.init` overwrites only dead slots; the core entries 0..4 are never rewritten. Otherwise allocation continues above every committed slot. Host pushes between submissions are Text, I64 or Bool and cannot introduce a Program. The same quiescent preparation restarts the definition-identity ledger empty: identities are session-stable ids checked against their recipes, plan and emission never read the ledger, and no earlier epoch's compiled body can run again, so each epoch admits at most 512 distinct identities while ordinary preparations still retain and check the whole ledger.
- The 8,192-key signature pool restarts only at a stricter, Program-free boundary. After a normal submission whose `compiled_programs_reachable` answer is 0, the runtime's read-only `programs_reachable` export runs the same `collect` mark closure and answers 1 if any marked cell is a Program (kind 4), recipe atom or concatenation (8, 9) or Syntax (10), or if the arena is malformed or failed; the engine reports both answers and the host refuses a report where a compiled Program is reachable but no Program is. Signature IDs are held at runtime only by those cells: Program interfaces, literal schemas and invocation witnesses in recipe atoms, and certified cells (16) that copy the interface of the Program they reference through a followed child, so a reachable certified cell implies a reachable Program. No other runtime structure carries an ID across a boundary: `$observed_program` and the recipe cursors are instance-private and also cleared by `collect`, which runs before every Calculator-v1 submission and zeroes the shared certificate page, and the host pushes only Text, I64 and Bool. On the compiler side the definition-identity ledger, whose recipes may name signatures, already restarts at every quiescent boundary, which a Program-free one implies, and earlier modules' compiled code is dead by the table-reuse argument. At such a boundary `prepare_program_free` starts the meter and the prospective pool from a fresh calculator pool, empties the published descriptors in the same epoch, and publishes from descriptor 0. The engine's `recordSignatures` keeps only `signatures.slice(0, first)` and refills `[first, end)`, so `first = 0` replaces the whole table, and `readSignature` bounds-checks every ID against it. Transaction provenance compares only the retained signature and descriptor prefixes, which are empty after a restart, and the key limit still applies within each epoch. Static literal Text and `text_end` are never rewound because live data Text may name static addresses. Neither monotonic quantity can approach its cap; see *Compile-cost headroom* for the bounds. Ordinary-profile WAT is byte-identical.
- Cross-line replay costs native time and memory and has separately identified host ceilings. It does not expand a guest `EvaluationWork` budget or make a failed line successful.
- Complete CALC conformance, independent numeric oracle/negative controls, AI-authoring benchmark and actual-Rust formal refinement require separate evidence. No result of those gates is claimed here.
