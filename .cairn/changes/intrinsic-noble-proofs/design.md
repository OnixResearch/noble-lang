## Boundary and entry point

`Intrinsic-Proofs-Draft` is opt-in and starts with actual UTF-8 `.noble` source submitted to the versioned `Declared-Modules-v1`-style `module name@version [ members ]` path. The new `contract` and `proof` members are admitted in the same immutable namespace snapshot as `def`, imports and exports, never as executable words. Their spelling and local/imported qualified references are resolved at module linking to exact module/version/declaration identities. Originally selected as new source forms, they now have **finite parser/resolver, source-checker and pinned independent Lean consumer support** demonstrated by six actual-source cases in the [immutable acceptance receipt](../../../verification/intrinsic-proofs/acceptance.json) and separately bounded in [status](../../../specs/STATUS.json); this is not a proof of full source-translation correctness or actual Rust refinement. Existing Core-Bootstrap submissions and MC1 `(contract 1 ...)` `.noble-contract` files remain unchanged; the module contract member elaborates into the existing MC1 typed contract semantics, not a second logic. Contract `subject` is a reference to an actual accepted pure definition, rather than a copied or producer-provided recipe.

## Concrete module grammar

In an opted-in module, the member parser recognizes:

```text
contract 1 Name [ subject QualifiedDefinition
  input [ Name Type ... ] output [ Name Type ... ]
  requires [ LogicalTerm ] ensures [ LogicalTerm ] ]
proof 1 Name for QualifiedContract [ ProofTerm ]
proof 1 Name : [ Proposition ] [ ProofTerm ]
```

`contract` fields are mandatory, exactly once in that order. The subject definition must have the full stated ordered pure stack interface and be independently accepted before contract elaboration. `requires` and `ensures` use the *existing MC1-v1* scalar/structural logical vocabulary and distinct `(in x)`/`(out y)` namespaces; `input` and `output` bind those names, and the consumer derives the complete partial-correctness proposition including preserved bottom-stack tail. In v1 the subject must be a closed, nonrecursive, resource-free pure Core-Bootstrap definition; no host operations, producer assumptions, totality or prefix-safety claims. The standalone `proof ... : [ Proposition ]` form only admits closed pure logical propositions, not an arbitrary `PC` claim: a program claim must use `for` and its consumer-selected contract. The `Name` of a `contract` or `proof` and the target component of its proof/contract reference or export use the scoped logical identifier `[A-Za-z_][A-Za-z0-9_-]*`, excluding existing reserved names. This does not widen ordinary module/definition/import-alias names, executable words or `input`/`output` binder names. `QualifiedDefinition` and `QualifiedContract` resolve to exact immutable identities. `1` is a required decimal grammar version, not silently inferred.

The module lexer keeps existing `#` comments, whitespace and ordinary `[`/`]` rules. **Only inside** `requires`/`ensures` and the proposition/proof bracket bodies, it switches to a logical mode recognizing balanced `(`/`)`, `:` and `,` as delimiters, without changing word parsing inside `def [ ... ]`; brackets delimit each balanced logical form and cannot inject an executable expression. A closing bracket or parenthesis in the wrong nesting context, unknown token, trailing form, escaped delimiter or a redefinition rejects the complete module before guest execution. `#` is never proof code; no raw Lean block, quotation interpolation, macro or tactic entry point exists. Source spans for declaration, binder, term and referenced word/contract are retained. Imports cannot publish unpublished/private proof or contract names. Proof `for` binds an exact accepted recipe, definition/version, schema/interface, logical context, model and contract revision; changing any of them produces a different obligation.

Two illustrative originally proposed source examples (the receipt independently records its canonical `.noble` witnesses):

```noble
module logic@1 [
  proof 1 polymorphic-reflexivity :
    [ (Pi (A Type0) (Pi (x A) (Eq A x x))) ]
    [ (intro (A Type0) (intro (x A) (refl x))) ]
]
module arithmetic@1 [
  def increment [ 1 + ]
  contract 1 increment-law [ subject increment
    input [ x I64 ] output [ y I64 ]
    requires [ true ]
    ensures [ (eq (out y) (add (in x) 1)) ] ]
  proof 1 increment-correct for increment-law
    [ (export-unary-I64
        (intro (tail Stack) (intro (x I64)
          (pc-sequence (pc-exact (exec-literal 1))
            (pc-exact (exec-add))
            (bridge (by-exact-append-assoc))
            (join (by-exact-result)))))
        (mc1-true-eq-wrap)) ]
]
```

`exec-literal` and `exec-add` are **not axioms**. `exec-literal` is restricted to a checked literal node of the exact subject; `exec-add` to the independently resolved builtin wrapping `+` and two checked `I64` operands. Their Lean expansion uses reviewed `NobleContracts.Rules.exec_lit_iff` (line 230), `exec_add_iff` (line 248), `pc_exact` (line 389), and `pc_sequence` (line 378), plus introduction terms. `pc_exact` has a *fixed initial stack*: the explicit `tail:Stack` and `x:I64` introductions instantiate it separately for each prefix/input. `Stack` is a dedicated logical sort admitted only in this contract-generated goal, never a Type0 code or guest value. `pc-sequence` combines exactly two adjacent subject slices with compatible full stacks and checks *both* required bridge and final join propositions. Set `s0 = tail ++ [.i64 x]`, `m0 = s0 ++ [.i64 1]`, `m1 = tail ++ [.i64 x, .i64 1]`, `t0 = tail ++ [.i64 (x+1)]`. The left exact PC has `P(s) := s=s0`, `R(s,m) := m=m0`; the right has `P'(m) := m=m1`, `Q(m,t) := t=t0`; the resulting `T(s,t) := t=t0`. `by-exact-append-assoc` MUST discharge the real bridge `∀ s m, P(s) → R(s,m) → P'(m)` by introducing all premises, eliminating the checked `m=m0` hypothesis, then applying whitelisted `List.append_assoc` to prove `m0=m1`. `by-exact-result` MUST discharge the real join `∀ s m t, P(s) → R(s,m) → Q(m,t) → T(s,t)` by introducing premises and returning only the checked `t=t0` hypothesis. Neither form proves an arbitrary implication; missing exact-result premise, different intermediate/result stack, altered operand order, foreign rewrite or omitted bridge/join rejects. The separate `by-defeq` rule, if used, emits `rfl` **only** when the actual open goal is definitionally equal; symbolic append associativity is not presumed definitional. The final obligation retains `BitVec 64` wrapping order `x + 1`.

The inner PC derivation is **not** the MC1 obligation by itself. `export-unary-I64` expects exactly the proof of `∀ tail x final, Exec acceptedCode (tail ++ [.i64 x]) final → final = tail ++ [.i64 (x+1)]`; it must extract this function from the inner PC evidence under the explicit binders and use the reviewed `NobleContracts.Obligation.exportedClaim_unaryI64` (lines 64–76). That theorem yields a typed exported claim with `True` precondition and an existential exact output. `mc1-true-eq-wrap` then supplies the two *checked* `exportedClaim_consequence` (Obligation.lean:34–42) implications connecting the independently generated MC1 `Holds` pre/post predicates to that exact output; its restricted elaborator must verify typed `input 0`, `output 0`, `add` and literal 1 IR nodes and reconstruct the Lean proof using `Expression.holds_true`, `holds_eq` and `evaluate` equations (Expression.lean:65–85,130–144), not stamp an arbitrary `Holds` result. Missing expression correspondence or a different predicate refuses this proof form. The resulting exact source claim is `∀ tail x, normal_return(increment, tail ++ [x]) ⇒ result = tail ++ [wrap64(x+1)]`, with the MC1 typed/pre/post boundary retained. It does **not** prove termination, Wasm correspondence or an unchecked alternate law. The canonical CONTRACT-18 `.noble` source now has finite source-bound elaboration and independent checking evidence; source-to-Lean translation correctness and actual Rust refinement remain separate open proof obligations. Existing Lean `increment_exec_iff`/`increment_pc` (Examples.lean:23–40) are comparison results, not authority to blindly stamp `increment-correct`.

## Predicative logical calculus

Judgments are `Γ ⊢ A : Type0`, `Γ ⊢ P : Prop`, `Γ; Δ ⊢ t ⇐ P`, and `Γ; Δ ⊢ t ⇒ P`; `Γ` contains resolved, total logical values/types and immutable reviewed rules, and `Δ` contains only explicitly approved local proof premises. `Type0 : Type1` is a meta-universe relation, **not** `Type0 : Type0`, and `Type1` cannot be quantified or inspected. Interpret `Type0` as an independently checked, closed inductive `PureTyCode` with constructors only for `Unit`, `Bool`, `I64`, `Text`, and recursively `Pair`, `Sum`, `List` of codes, plus decoding `El : PureTyCode → Type` to their total pure semantic values. A binder `(A Type0)` lowers to `∀ (A : PureTyCode), ... El A ...`, **not** unconstrained `∀ (A : Type), ...`. Each code MUST have a recursively checked interpretation `tyOf : PureTyCode → NobleContracts.Ty` and value embedding `encode_A : El(A) → NobleContracts.Value` with `HasType (encode_A x) (tyOf A)`, faithful equality on these encoded values, and no decoding of ill-typed/partial values; this correspondence to Model.lean's tagged `Ty`/`Value`/`HasType` is an open model obligation, not an assumed cast. Every introduced/applied/substituted type code is independently validated; there are no constructors, casts or normalization rules smuggling Resource, Program, Syntax, host capability, effectful/nominal opaque wrapper or impredicative universe encoding into `PureTyCode`. Only structurally valid, recursive `Data`/`Capture`-eligible code instances and defined uniform operations are admitted. Dependent `(Pi (A Type0) P)` is a proof-level type universal; `(Pi (x A) P)` is a value universal. Neither is a runtime-polymorphic `Program` interface, first-class runtime `Type`, general refinement inference or implicit coercion. `(Eq A a b)` is only well-formed for total values `a,b:El(A)`; heterogeneous equality, partial selector values and arbitrary program equality are unsupported. This Eq is *not* MC1's potentially undefined `(eq ...)` evaluator; any bridge to a contract predicate requires the exact typed `Holds`/`evaluate` proof, so polymorphic reflexivity by itself proves no program property. `(PC subject P Q)` can be introduced only via the independently checked `for` contract and reviewed semantics rules, never by a fabricated producer proposition.

`intro` checks the expected Pi and extends its binder context; `apply` eliminates Pi with a checked type/value argument and capture-avoiding substitution; `refl` checks `Eq A a a` by bounded definitional equality; `subst` eliminates equality with an explicit well-formed total motive `M : A → Prop` and proof `M(a)` to obtain `M(b)`. These forms provide dependent equality elimination; `sym`/congruence, if exposed later, must be derived. Named `use` may reference only previously accepted immutable proof identities with exact transitive context/assumption dependencies; arbitrary `axiom`, `admit`, `sorry`, `unsafe`, general recursion, unbounded reduction and native callbacks are forbidden. Definitional equality reduces only strongly normalizing logical lambda/substitution and total canonical scalar/structural computations under specified wrapping semantics, not Noble program execution, tactics, Lean `native_decide` or host calls. The bounded checker has finite syntax, finite reference DAG, decidable type/value equality for admitted types, structural substitution/normalization, explicit work/size/depth/dependency/memory limits shared across parsing and proof checking. Exhaustion/unsupported/internal failure are distinct and never accepted. Positivity, consistency and adequacy of the rule fragment relative to reviewed semantics are separately open proof obligations.

## Lean-first trust, erasure and admission

A producer parses/infers but a separate acceptance path checks the untrusted Noble declaration and resolution against a host-selected expected contract/claim/context before any proof acceptance. It produces a restricted, closed Lean term from the *typed Noble term* and independently checks its elaborated type against the **separately regenerated exact MC1 obligation** under pinned reviewed pure Noble model/rules with transitive axiom/library inspection and isolated resource/time limits. No user Lean import/declaration, `by` tactics, `sorry`, producer-generated theorem statement, or unchecked extension enters the permitted proof library. Lean is the first independent checker target, not a substitute for a Noble language proof calculus. Correctness/refinement of the parser, accepting typing judgment, translation and reference-model/actual subject correspondence remain distinct **open** obligations even if a generated Lean term kernel-checks. Bend2 is a comparative backend/design study, not a proof optimization/kernel route.

Reuse Noble's existing VT-ROLE-01/VT-SCOPE-01 Charon → Aeneas → Lean policy for **actual production Rust** module parser/resolver, proof checker, typed Noble-term→Lean lowerer and admission decisions, with exact source inventory and independently reviewed external models; new extraction/refinement results are not claimed. Charon/Aeneas do not parse or typecheck Noble proof source, and the Rust refinement lane is separate from the strict independent Lean check of the user-authored Noble theorem. Eurydice/Scylla and Bend2 provide no relevant proof kernel or backend dependency for this selection.

Proof terms are compile-time-only declarations erased before ordinary Noble/Wasm code emission; no guest value or effect, recipe/DefinitionId change for the unchanged executable program, implicit proof search, guest proof invocation, proof-provider call or authority grant follows. Proof metadata/evidence companions retain their independent exact subject, contract, assumptions and checker/policy versions under MC2. Proof-required release separately validates applicability for actual inputs, exact accepted artifact/build correspondence, host authorization and current policy. Ordinary rank-1 programs remain proof-optional; a source-proof failure rejects that opted-in proof/module submission, not previously accepted definitions or proof-free runs. Program-typed parameter dependence and whole computational dependent runtime are explicitly outside this profile.

The candidate author can edit a module-local `contract 1`, so its `for` proof alone does **not** establish that a release owner's intended law has been proved. For any owner-law/proof-required release, the independent consumer MUST compare the complete elaborated proposition (including actual subject/interface, requires/ensures, normal-return scope, initial/final namespaces, assumptions, model/schema and versions) with the immutable **owner-frozen law identity and statement established before candidate edits** under VC-OWNER-01. A modified `requires [ false ]`, weakened `ensures`, producer-supplied model premise, stale law revision or unrelated proof can be well-typed source but cannot satisfy that owner policy; admission fails even if Lean accepts the weaker theorem. A revised owner law needs a fresh owner decision and fresh exact check, never silent rebinding.
