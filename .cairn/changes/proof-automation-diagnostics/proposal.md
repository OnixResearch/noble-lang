## Why

Noble contracts already have exact independently generated claims, strict Lean acceptance, `noble verify`/`noble explain-proof` (MC1) and `noble verify-module` (Intrinsic-Proofs-Draft). They give an author little help in *producing* a proof or understanding why one failed. `verify` without evidence returns `unknown` and performs no proof search. The source checker reports a single span and message. No obligation map, goal/context view, counterexample workflow or helper expansion exists. Issue #6 asks for a bounded design and evaluation plan, not an implementation, that makes contracts easier to prove and debug while every proof producer stays untrusted. (related: VC-TOOL-01, VC-TOOL-02, VC-TOOL-03, DX-PROOF-01)

## What Changes

- Design a source-located obligation map. Each subject, contract, ordered input/output stack with preserved bottom tail, pre/postcondition, intermediate bridge/join site, wrapping-`I64` arithmetic and assumption gets a stable key and links back to its source span. r[PAUTO-MAP-01] (related: VC-INPUT-01, VC-LOGIC-06, VC-NUM-01)
- Compare three producer approaches: an external tactic/SMT producer, reviewed proof templates, and bounded hole/helper suggestions (`intro`, `apply`, `refl`, `subst`, exact `use`, reviewed composition). Each producer can only emit an explicit candidate. That candidate goes through the existing source checker and the independently pinned Lean consumer, which check it against the separately generated exact claim. Accepted evidence replays without rerunning the producer. r[PAUTO-PRODUCER-01] (related: VC-TOOL-03, VC-INTRINSIC-03, VC-INTRINSIC-05)
- Treat solver models and generated inputs as candidate counterexamples. Distinguish three things: a candidate model, a checked semantic refutation (`disproved`), and an observed compiled execution. Retain the input, the output or trap, the source identity and the violated predicate. r[PAUTO-CEX-01] (related: VC-TOOL-02)
- Design a goal/context view and status indicators that are derived only from the independent checker. The view distinguishes checked, incomplete/unknown, unsupported, refuted, exhausted/timeout, internal failure and stale. Partial correctness is never shown as termination or as artifact correspondence. Status is invalidated after a source, contract or dependency change, while saved immutable evidence is kept for its original subject. r[PAUTO-GOAL-01] (related: DX-HOLE-01, VC-ADMIT-04, VC-LOGIC-01)
- Recommend one small first profile, `PAUTO-P1`: the obligation map and goal view, reviewed templates for the existing unary-`I64` literal/add skeleton, pure-fragment helpers, and boundary-value counterexample replay. External SMT/tactic producers are deferred to a later profile. List the follow-on implementation and proof obligations.

## Impact

This change adds a design-only active change with ADDED `PAUTO-*` requirement deltas for `program-contracts` and `developer-experience`. The scenario designs `PAUTO-CASE-01` through `PAUTO-CASE-16` live inside `design.md` with state absent/not-run/open/unassessed. It changes no compiler, checker, CLI, report schema, Lean library, conformance JSON, canonical spec, status/roadmap record, generated view or ledger. It adds no new trusted solver, axiom, rule or proof syntax. No proof, implementation or execution result is claimed. Reusable call rules (#7) and artifact correspondence (#10) remain separate workstreams. Implicit-argument elaboration (#12, `implicit-proof-arguments`) builds on this change's goal view.
