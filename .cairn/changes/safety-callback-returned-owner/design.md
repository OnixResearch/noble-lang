## Context

Canonical S-CASE-08 (`specs/conformance/safety-cases.json`) names `callback-handle-matrix` with stale-generation, wrong-kind and wrong-context mutations and expects `callback/invalid-result` with `trusted_values_created:0`. It has no implementation, execution or evidence; proof is open and trust unassessed. Existing S-CASE-02's host-selected byte-region owner and S-CASE-06's host-retained Directory exercise other boundaries; their historical receipts do not establish callback-returned owner ingress. The production resource table already has namespace, kind, context, generation, liveness and retirement concepts. This proposal does not alter S-CASE-04/06 or their active changes.

## Decisions

### Decision: Select one actual owned-result callback boundary

**Choice:** Pin `crates/noble-wasm/wit/callback-owner.wit`, world `noble-test:callback-owner/bounded@1.0.0`: imported `tokens.issue() -> own<token>` and `tokens.consume(own<token>) -> s64`, exported `check() -> s64`. Compile `verification/scase08/guest.noble` with `tokens.issue tokens.consume` unless a necessary source adjustment is recorded and frozen. The production CLI is `noble component callback-owner COMPONENT MODE WIT WORLD EXPORT=SOURCE`, with MODE `authentic`, `stale-generation`, `wrong-kind` or `wrong-context`. The invoker supplies the **complete** WIT/world/export-source recipe, not a candidate-attached identity. Before `Host::new` registers any owner and before Store/guest execution, independently prepare and compile that exact recipe with pinned tools and compare its final component bytes to COMPONENT; mismatch refuses at admission with no guest requests or owner and does not count as S-CASE-08.

**Rationale:** An arbitrary component or a claimed source could otherwise produce the desired report without executing the selected guest/callback. The authentic run of the same component makes the rejected result distinguishable from a broken import or a compiled guest that never consumes an owner. r[S-HOST-01]

### Decision: Validate host-created claims before trusted construction

**Choice:** After recipe byte-match, `Host::new` pre-registers one pending authentic owner and only the selected mode's necessary real table fixture before Store/guest execution. `authentic` needs no fixture. `stale-generation` first registers and retires generation 1, then registers the live pending owner in that reused slot at generation 2; `wrong-kind` or `wrong-context` registers a single additional live owner with respectively different kind or foreign context. The first actual guest `tokens.issue` import does **not** create an owner; its host callback selects the retained authentic pending claim or the selected hostile fixture claim. Contexts and table namespaces are bounded, nonwrapping and distinct where required: current/foreign contexts within a host, namespaces across simultaneously live hosts; allocation exhaustion refuses. Matching slot/generation alone never establishes authority. A separate cross-host control should copy a real foreign claim while equal slot/generation are live.

Validate the returned claim against the host's retained table identity, slot, generation, expected token kind, current invocation context, liveness and required owner rights at the **host callback ingress**, before calling the Wasmtime owned-resource constructor (`ResourceAny`) or publishing a trusted Noble value. A validation error is an `invalid-result` **host** observation, never a guest-returned error string or a Wasmtime trap retrospectively labeled as the intended result. Only authentic admission publishes one `Val::Resource` WIT-owned guest representation. The host retains the actual `Table::Owner` and cleanup obligation rather than invoking `Table::transfer`; the guest's `tokens.consume` request consumes that WIT representation once, accounts one protected operation and permits the host to release its retained table owner once. A hostile issue stops after its first guest request and cannot invoke consume. No numeric slot alone or guest-supplied metadata can manufacture ownership. r[S-HOST-02] r[S-MEM-02] r[RA-OWN-01]

**Rationale:** The unsafe transition under test is output-to-trusted-resource construction, not subsequent wrong-handle use. Real preexisting table states let the same validator discriminate an old generation, wrong kind and foreign context, rather than rejecting arbitrary malformed labels.

### Decision: Bounded settlement and measured result

**Choice:** The `noble-callback-owner/v1` report records `stage`, `outcome`, `trusted_values_created`, `protected_operations`, `released_owners`, `fixture_releases`, `live_owners`, `native_pins`, and `guest_requests` from actual callback/table events and mode-selective fixture lifecycle. In that numeric field order the three hostile modes each report `callback/invalid-result`, `0/0/1/1/0/0/1`; authentic reports `callback/accepted`, `1/1/1/0/0/0/2`. `released_owners:1` counts exactly the pending authentic obligation consumed in authentic mode or host-retired in hostile modes. `fixture_releases:1` on each hostile mode accounts the stale setup retirement **or** the one wrong-kind/foreign-context fixture cleanup; authentic has no fixture and reports zero. An invalid claim does not abandon the retained pending owner, leave a live fixture or native pin, or cause a second release. Check the complete report and independently measured table state, not just a matching output string. The canonical record's three exact expected fields remain authoritative; the additional counters are acceptance controls.

**Rationale:** Construction can fail safely while leaking a pending owner, a live hostile fixture or a pin; cleanup accounting must observe obligations not available to the guest. Each mode creates only the table states it needs, and its one possible fixture release is distinct from the single pending authentic owner release. r[RA-CLEAN-03]

### Decision: Immutable prepromotion acceptance and conditional cutover

**Choice:** Gate the native proposal/design/tasks now, keeping these deltas unsynced. Once production and the separate gate stabilize, freeze exact canonical input/expected/state, complete guest/WIT/CLI/table source and build selections, component and receipt hashes, commands and raw outputs on a new immutable **prepromotion** source snapshot. Run all four actual compiled guest/production host modes and real table-state/context controls, a positive consume and a mismatched-recipe admission refusal. Record observed report fields, exit status, zero failures/integrity failures, explicit assumptions and independent settlement/correspondence checks. Preserve every previous S-CASE-04/06/S-CASE-02 and older receipt. Only after a pass, the promotion owner may preview/execute native sync, update the case's implementation/execution/trust/evidence and derived views/status, and run separate postpromotion assurance. A later source revision needs its own chronological replay; no archive without full scoped assurance.

**Rationale:** Proposal validation and document regeneration prove neither guest execution nor callback owner-law; binding the evidence before editing its canonical subject avoids retroactively claiming acceptance from changed source. Proof remains `open`, and `trust:explicit` records explicit runtime assumptions, not accepted proof.

## Risks / Trade-offs

- This finite synchronous world is not general host-callback safety or a new untrusted serialization format. Wasmtime 40.0.2, component ABI conversion, host-invoker source/WIT trust, selected compiler/assembler and actual resource-table embedding remain explicit trust assumptions.
- Real retired-generation setup or a live wrong-kind/context fixture cleanup must not inflate `released_owners:1`; account only the selected mode's fixture (`0` authentic, `1` hostile) separately without treating a fabricated label as a table state. Equal numeric slot/generation in distinct namespaces must still refuse.
- Neither a checked local table transition nor compiled control is a general Rust/Lean owner-law refinement, backend correctness proof, Octet assurance or guarantee of native cleanup after arbitrary asynchronous work; all remain open independently.
