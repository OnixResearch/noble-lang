## Why

Noble issue #3 asks how the ordered stack interfaces can make ownership and lifetime guarantees compositional, including saved Programs and their captures. It also asks that the language/checker contract stay separate from any backend allocation strategy. The current specifications already settle the source-level resource discipline: §4.3 eligibility, K-TYPE-01/02, K-PROG-02/05/07/08, K-RES-01..04, K-STACK-01, K-CONTROL-01 and K-DEF-01/02. The runtime lifetime unit of a saved Program is still undefined. P-PACK-01 names a *portable* dependency closure of code and contracts. No requirement says which executable members a saved Program keeps alive inside a running instance. Those members include compiled bodies, module globals read by named calls, table entries, recipe cells, static Text and signature entries. Nor does any requirement constrain a non-tracing reclamation algorithm, a scratch-arena reset or a future source-level borrow. RA-SCOPE-01 and WI-RES-02/05 explicitly defer source borrows to "a separate lifetime contract". This change supplies that contract as a design. It selects no syntax, implementation or allocator. It builds on `K-RES-01`, `K-PROG-07`, `P-PACK-01` and `WI-RES-05`. r[OWN-PKG-01] r[OWN-BORROW-01]

## What Changes

- Recommend one bounded ownership model. The model keeps Core's existing `Data`/`Capture` and move-only resource rules as sufficient for the ordinary profile. Any later opt-in borrow profile is limited to second-class, scope-tagged borrows. Such a borrow is created only by a `dip`-like scope combinator. It is non-`Data`, non-`Capture` and never stored in aggregates, recipes, continuations or saved Programs. A checker escape test rejects any output or Program interface that mentions the scope tag. r[OWN-BORROW-01] (extends `K-RES-02`, `RA-TYPE-02`)
- Define the owned saved-Program package as the complete executable lifetime unit. The unit comprises code, exact named dependencies (including module globals and table entries read by compiled calls), captures, recipes, static data and required metadata. Releasing module roots, replacing definitions, resetting arenas or publishing slots must not remove a member that a live owner still reaches. r[OWN-PKG-01] (extends `P-PACK-01`, `H-LIVE-03`)
- State the conditions under which non-tracing guest-cell reclamation is safe. Every owning edge kind must be counted. Acyclicity must be argued by logical birth order, never by recycled handles. Counters and epochs must be bounded and never wrap, and a cell may be reclaimed only when no counted owner of any kind remains. Arena reset or rollback is allowed only below every retained owner. Abnormal-exit cleanup belongs to the host, and data storage cleanup never releases a host resource. r[OWN-RECLAIM-01] r[OWN-SCRATCH-01] (within `S-MEM-04`, `BE-RESOURCE-01`)
- Compare three strategies with costs and profile compatibility: scratch arenas with retained packages, closed copied packages, and immutable sharing with deferred reference counting. List proof obligations by layer: abstract model, checker, Rust lowering, Wasm runtime and host ledger. Design twelve unexecuted OWN-CASE conformance scenarios, and list the decisions and evidence still needed before any implementation claim. r[OWN-EV-01] (refines `V-RESOURCE-03`)

## Impact

- **Files**: only this active change: `proposal.md`, `design.md`, `tasks.md`, and ADDED deltas under `specs/language`, `specs/safety` and `specs/evidence`. Canonical `.cairn/specs`, `specs/conformance/*.json`, generated views, the ledger, the roadmap and status files stay unchanged. The OWN-CASE scenario designs live only in `design.md` and are absent/not-run.
- **Coordination**: allocation policy belongs to `allocation-strategy-contract` (#5). Live-slot version retention and in-flight pinning build on this contract in `live-reference-lifetimes` (#1). Issues #4, #9, #11, #14 and #15 consume these obligations; none of them is changed here.
- **Testing**: document validation and the proposal/design/tasks gates only. No runtime, checker or proof result is executed, inherited or claimed. Every argument here is a written conditional design argument, not a mechanized proof.
