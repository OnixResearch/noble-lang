# I64 sequential tick runner: frozen continuation criteria (revision 1)

Issue #128. These criteria must be committed **before** any #128 measurement. A receipt must name this file's SHA-256 and the source commit on which it ran. Do not revise the rule after seeing data; a changed experiment requires a separately versioned preregistration and retains this decision. The runner is opt-in; this is a decision about further work, not default activation.

## Selected profile and scenarios

Use the `noble-tick-i64/v1` profile in README.md. A tick calls the runner exactly once, with one stateful stream; no parallel rows, effects, F32, cache lookup, specializer or batch execution. Compare three implementations on **the same ordered operations and initial states**: (R) checked packed tick runner, (G) ordinary repeated checked graph evaluation with host-managed state and control slots, and (N) straightforward host-native Rust wrapping-I64 recurrence with equivalent update/reset/observation handling. Each operation, including rejected updates and resets, remains in the denominator of whole-trace costs. The native comparison is not a substitute for graph admission: its separate setup costs must be stated as not applicable, not zero-cost graph checking.

Preselect three scenarios: A: one-state recurrence `s' = s + c * input`, visible output `s'`, including positive/negative inputs, overflow at I64 limits and an update of `c`; B: two-state asymmetric recurrence `s0' = s0 - c0 * input0`, `s1' = s0 + s1 * c1 - input1`, visible outputs ordered `[s1', s0']`, with distinct controls, swapped input signs and overflow; C: A followed by explicit reset to a different subtracting DAG `s' = s - c * input` with separately admitted initial state/controls even when the partition is unchanged. Record exact graph export/model identities, input/control/state vectors and operation sequence; otherwise a timing row is invalid. Use stream lengths 32, 512 and 4096 successful ticks per scenario, with a control change after ticks 8 and thereafter every 64 ticks where the length permits, and a single reset at tick index 256 in C for lengths >=512 (at index 16 for length 32). Preserve refusals as distinct extra operations in the trace, not as silently skipped samples. The finite correctness corpus also includes the README's adversarial stale, malformed, budget, cancellation, terminal and counter-overflow cases; these may be measured separately but never substituted for the selected accepted scenarios.

## Reporting: costs that must remain separate

Measure graph/checker/schedule admission and initial `prepare` as **graph preparation**; a reset's admission and storage preparation as **reset**, separately from a control update's validation (**control admission**) and activation (**control publication**). Include refused calls and their cost, plus cleanup/drop cost. Report first executed tick after prepare, first after update, first after reset, and steady warm ticks separately; first means first in this process, **not** page-cache-cold. Report complete trace wall/CPU time inclusive of setup, resets, updates, refusals and cleanup; retained state/output/workspace/schedule bytes and peak resident memory separately; any allocation events/bytes per phase only if an actual allocator instrument is used, otherwise `unmeasured` with reason, **never 0**. Scratch peak is not retained bytes. Sample count, p25/median/p75 and sample dispersion accompany each time category; negative or absent stage data invalidates a comparison. A graph update is an explicit reset, not a control update. Warm register reuse cannot by itself imply no allocations or deterministic latency.

Run one untimed correctness replay per arm, then 11 interleaved rounds of each arm on the same ordered trace; the first round is labeled first/process-warmup and the remaining 10 determine warm medians. Record compiler optimization profile, pinned rustc, host/CPU/OS, source commit/tree cleanliness, graph/schedule/export identity, exact workload bytes/digest, limits and seed (if generation is used). Graph and native work must both consume the same observations, so dead-code-eliminated native loops are invalid. The host is shared: wall-time findings are observations, not real-time guarantees. Do not compare the old W3-L graph or #41 independent-row data as if it were this workload.

For **each** baseline B in {G,N}, compute independently:

- `saving_B = median(warm_tick_B) - median(warm_tick_R)` (time per successful tick, with the same trace mix);
- `incremental_setup_B = (R prepare + R reset + R control admission/activation) - (B equivalent setup/reset/update costs)`, for the selected trace, with stage totals separately reported rather than hidden in this subtraction;
- if `saving_B <= 0`, `break_even_B = undefined (no positive marginal saving)`; otherwise `break_even_B = ceil(max(0, incremental_setup_B) / saving_B)` successful ticks. If update/reset mixes change with length, recompute from that length's own stages; do not extrapolate one mix to another. Also compare direct **whole-trace** medians, which supersede amortization estimates for the measured lengths.

## Hard correctness gate and decisions

Correctness requires exact agreement of independently computed signed wrapping-I64 **state and ordered visible output at every accepted tick**, and full active tuple/epoch/next-tick/output equality after every operation including refusals. All selected profiles must be independently admitted against their real graph interfaces. Counter overflow, stale/duplicate requests, malformed/over-budget operations, cancellation and reset must refuse/transition as documented without partial commit. Seeded faulty selectors must be detected, with the injected fault named; a passing implementation-only self-comparison is insufficient. Exported traces must replay through the bounded independent Node model and preserve source, graph, schedule and export identities. Any mismatch or missing/unmeasured mandatory correctness evidence is an unconditional **NO-GO** and makes performance numbers non-decisional.

If correctness passes, further **opt-in** optimization exploration is GO only when all three scenarios show, at both 512 and 4096 ticks: (1) runner warm median is at most **0.90 × ordinary graph median**; (2) runner whole-trace median, inclusive of its actual preparation/reset/update/refusal/cleanup, is at most **0.95 × ordinary graph whole-trace median**; (3) runner whole-trace median is at most **1.25 × native whole-trace median**; (4) both baseline break-even counts are defined and at most **4096** successful ticks; (5) runner peak scratch, retained bytes and peak RSS each grow no more than **1.25 ×** the corresponding ordinary graph value at the same trace length, with 32→4096 retained growth explained by actual retained versions, not hidden unbounded retention. A zero baseline for a memory metric requires an explicit absolute byte delta and a reviewed decision; it never yields an infinite/automatic pass. Timing measurements absent, too noisy to distinguish thresholds (interquartile intervals overlap the boundary), or inconsistent with measured whole-trace costs produce **NO-GO / inconclusive**, not a favorable assumption. A 32-tick row is mandatory for overhead reporting but not a performance GO threshold.

GO only authorizes another separately reviewed opt-in experiment, never a faster-than-native or allocation-free claim. Otherwise retain **NO-GO** and the failing categories without changing the frozen cutoffs. #14 Phase C **STOP** remains in force (warm W3-L graph ≈9.71 µs against native ≈1.27 µs); #41 independent-row batch **NO-GO** remains in force (4096/65536-row speed and resident growth failed its frozen rule). Neither historical outcome is revised by a successful different sequential workload. A proposal to change either requires its own issue, frozen rule and retained independent evidence; the #128 result cannot silently reopen them.
