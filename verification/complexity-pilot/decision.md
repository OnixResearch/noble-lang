# Complexitylib pilot decision for issue #80, U3/U4

The isolated Lean 4.36.0-rc2 project is **GO** as a reproducible imported-subset proof lane. It builds the original finite model and a machine-grounded polynomial-time certificate for **only its unary-width prefix parser**. It is **NO-GO** for a polynomial-time claim about the entire `validateEncoded` function, for a costed implementation of that function, and for any bound on the deployed Rust/Wasm `layout::check`. No finite-domain lookup or constant-time `Nat → Node` oracle is used in the certified parser.

## Why the decoder cannot be discharged by the current unary recipes

The canonical model `encodeNat` writes a *unary width* followed by that many binary value bits. A valid input of value `2^w - 1` has a natural field of length about `2w + 1`, but materializing the parsed value with Complexitylib's `encUnary` needs about `2^w` bits. A general `decodeNatPrefix : encBits → encOption (encPair encUnary encBits)` machine certificate therefore cannot follow from a polynomial output-length bound. The unary-prefix certificate is valid because its parsed width is at most the number of prefix bits. The remaining parser must use a binary value encoding such as `encNat`, or avoid materializing unbounded values; its recursive list decoder must prove a malformed length never triggers work proportional to an attacker-declared count without consuming corresponding input bits. The binary-output probe above still lacks a checked fixed-bits parser and option-composition proof. Do not substitute the prefix certificate for a `validateEncoded` certificate.

This is a scoped decision, not a global negative result for Complexitylib or for the mathematical possibility of a polynomial validator. The project deliberately does not upgrade the main foundation toolchain and does not make the #43 packed-schedule equivalence claim. #64's measured scaling is a cross-check, not a proof.
