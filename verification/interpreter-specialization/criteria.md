# Interpreter-specialization first-projection criteria (frozen before measurement)

Issue #34, first projection. No prior #34 Rust interpreter measurements are imported into this campaign. This document is committed before the measurement producer is run and must not be changed to fit the results.

## Subject and observation

The source language is exactly two sequential accumulator instructions. Each instruction is one tagged byte: `0=add`, `1=sub`, `2=mul`. A program is exactly two bytes; all other lengths and tags refuse before graph construction. Its accumulator starts at dynamic I64 `x`, and each operation combines the accumulator (left operand) with dynamic I64 `y` (right operand). All operations wrap modulo 2^64; there are no traps, branches, effects, unbounded recursion, or stack operations. Consequently, stack underflow/overflow is inapplicable to this family (a different stack family would require new criteria). An unsupported program, graph, admission or budget outcome is a refusal, never a default result.

`I` is a single independently admitted Noble `ngraph-i64/0` Program with eight I64 inputs: six static one-hot coefficients (three per tagged instruction, in add/sub/mul order) and two dynamic inputs (`x`, `y`). It applies all three arithmetic operations per instruction and sums their one-hot selected results, with fixed order and no dynamic branch. The two program bytes are decoded once to one-hot coefficients, *not* read by the residual at run time. The interpreter is strict but only total wrapping operations are admitted. Static binding uses #32 `specialize` under `ngraph-pe/0`; deterministic algebraic rewrites, if implemented, must preserve wrapping I64/Bool observation for all checked graphs within the slice. The residual is emitted as Noble source and independently admitted via the ordinary source/kernel/extractor path. #33's in-process positive-only cache is opt-in; every hit is revalidated/re-admitted, and no native executable is shared through the cache.

The correctness claim is `Obs(I(one_hot(s), x, y)) = Obs(run(readmit(mix(I, one_hot(s))), x, y)) = Obs(ref(s, x, y))` on all valid two-byte programs and all I64 pairs, where normal I64 equality is the observation relation. A malformed source or exceeded budget must refuse; the claim does not equate the work, failure site or budget used across the two programs. The existing foundation `FirstProjection`/`OperandForwarding` theorems prove an abstract 24-node packed-graph model for all nine programs, not Rust specializer correctness, graph extraction, ordinary Program admission, Wasm correspondence, or execution costs. No model-to-Rust theorem is claimed.

## Preselected campaign

* Exhaust all nine ordered two-opcode programs, test each against boundary pairs including `MIN`, `MAX`, `0`, `1`, `-1`, noncommutative `7,2`, and at least 256 deterministic `SplitMix64` pairs (seed `0x34f0_2026_1114_0001`). Wrong static binding, wrong opcode, operand reversal, and stale captured dependency controls must disagree on an identified vector. Refusal cases include wrong length, invalid tags, specialization variant cap zero, and residual node cap below the interpreter size. All cases must re-admit the emitted residual normally.
* Inspect and retain one text residual per ordered program. For each, dynamic input variation must work and all three-way opcode selector multiplications and unselected arithmetic branches must be gone from its live graph; one or more selected arithmetic operations remain. Merely storing the static program in a wrapper fails this gate.
* For each ordered program, repeat setup 11 times, with fresh sessions for misses and a reused session for hits; time independently: specialization, source emission, ordinary residual admission, backend graph build, cache lookup/content validation, cache admission, cache publication, cold first execution. For warm performance, preallocate reusable workspaces, warm each pathway before 31 independently timed samples of batches of 1,024 identical `(x,y)` pairs. Record p25/median/p75/min/max and sample counts, not just a single duration. Compare the original interpreted graph, the residual, a direct two-operation ordinarily admitted Noble graph, and an independent host-native wrapping evaluator on the *same* batch. Label separately any one-shot CLI prepare/compile/instantiate costs measured; never mix them into a warm-code speedup. Report actual residual/source bytes, variants, cache retained bytes, compiled retained bytes and scratch/workspace bytes when available; otherwise `unsupported` with the precise missing instrument (never silently use zero).
* Pin source HEAD, available CPU/OS, Rust/Node compiler versions, backend/compiler revision, CLI digest if used, optimization profile, graph budgets, dataset seed and rows, and session cache limits/state in the receipt. Output is retained only after a clean committed source revision; receipt records that revision. If a stage is unavailable it must have a named reason.

## Continuation gates

Hard first-projection gate: all differential/refusal/control/independent-admission assertions pass, and every inspected residual removes static dispatch without sacrificing dynamic inputs. A failed hard gate is `NO-GO` for later projections regardless of timings.

Use *median per-evaluation* warmed costs on identical inputs to define savings = original-interpreter median minus residual median. When savings <= 0, amortization is **undefined (no positive savings)**, never reported as zero or as an invented break-even. Otherwise incremental setup = specialization + emission + independent admission + backend build **minus any setup that the comparison pathway would also pay**, from the separately measured setup medians, with no subtraction of cache hits as a hypothetical saving. Break-even calls = ceil(max(0, incremental setup)/savings). Report full setup and cache-hit pathways separately. Timings are observational on a shared host; do not claim a stable speedup from one run.

Second projection: `GO` only if the hard gate passes, at least 7 of 9 programs show >=20% warmed median saving, each positive-saving program breaks even within 10,000 calls, residual bytes <= original interpreter bytes, and a reviewed accepted representation of the specializer itself plus a finite specialization/termination bound exists. Otherwise record `NO-GO` with the failed conditions and precise reopening evidence. Third projection: `GO` only after second-projection feasibility/equivalence is established, with a self-representation of `mix`, measured generation costs and repeated-use benefit under a new frozen protocol. Otherwise `NO-GO`; no self-application follows from a Rust specializer of Noble subjects. Neither later projection is authorized by an enticing microbenchmark alone.
