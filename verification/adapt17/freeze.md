# ADAPT-17 lowering audit and experiment freeze

## Selection and scope

The post-M3 managed-memory layout trial is selected, following the owner instruction to implement every open issue. This is an optional, resource-free finite experiment under `BE-LAYOUT-01`; it does not reopen M3, promote resource-positive Wasm/WIT behavior, establish a universal equivalence theorem, or change the default backend. The selected default remains the current managed-linear-memory compiler regardless of the outcome. The experimental lowering is opt-in and must report when it falls back to the selected baseline.

The two arms are:

1. **Selected baseline:** `noble_wasm::source::Compiler::new()` and its current managed-linear-memory lowering.
2. **Candidate:** an explicitly selected experimental lowering for the statically known finite-Sum case fragment. An eligible sequence is exactly a scalar literal (`I64`, `Bool`, or `Unit`), adjacent `inl`/`inr`, two static quotation operands, and adjacent `case` in one already checked program. The candidate preserves the source recipe but leaves the literal on the operand stack, avoids boxing it and allocating the transient Sum wrapper, then enqueues only the statically selected quotation. This is a bounded ANF/known-arm specialization, not a general nominal-ADT compiler. Every unmatched operation—including dynamic values, captures, reflection-reachable values, unresolved calls, and unsupported layouts—uses baseline lowering. The WAT report records specialization and baseline-fallback operation counts. No candidate preparation request is permitted.

The frozen matrix is the four ADAPT-17 workloads (`two-arm-variant-both-arms`, `nested-pair-list`, `runtime-captured-quote-and-composition`, and `reflection-only-reachable-recipe`) × both optimizer settings (`off`, `on`) × both lowering arms, plus the five case-defined controls. Runtime-supplied values are fixed after module compilation: I64 `30` for both known Sum arms, I64 `7` for capture-and-composition, and I64 `9` for the reflection-only recipe; the nested Pair/List workload has no runtime input. Every candidate is measured against the same checked source, typed input stack, post-compilation values, limits, and ordered effects.

## Lowering and runtime audit

The checked source path reaches `source::plan::operations::lower_node`, which resolves each node's checked interface and dispatches nominal constructors/matches through `source::plan::operations::nominal`. `source::plan::allocation` assigns quotation programs and data segments. `source::emit::functions` emits the planned operation sequence; `source::emit::nominal.wat` implements the current nominal constructor, projection, and match behavior. The nominal variant cell retains its tag plus the resolved module/ordinal/arm marker, and match checks the live cell and identity before unboxing its payload and scheduling exactly one branch.

The selected `source` runtime uses managed linear-memory cells. `runtime/linear-storage.wat` lays each cell out as 48 bytes; `runtime/accounting.wat` charges 48 guest logical bytes for each reserved cell, checks `allocation_limit`, and records allocation/release/peak/live counters. The host-visible runtime ABI imports the allocation limit and supplies bounded recipe, depth, operand, continuation, and step limits. The current source ABI's ordinary default is 196,608 allocation bytes, 256 recipe leaves, 256 program depth, 2,048 operand bytes, 4,096 continuation bytes, and 100,000 steps (`crates/noble-cli/src/core/runtime/abi.json`).

Only the explicitly selected trial compiler modes append a trial-only `cleanup` export to each disposable run module; the default source ABI and default CLI output do not expose it. The measured baseline uses the ordinary lowering plus this export: the gate removes only the exact cleanup fragment and requires the remaining WAT digest to equal default CLI compilation for the same source. After the host records the complete report and ordered stack/request prefix, cleanup resets transient operand, continuation, observed-program and recipe cursors plus the one-shot submission guard (`generation`), then rolls back guest cells to the invocation's measured heap baseline. It preserves failure/phase and host effects; stale bytes behind reset cursors are unreachable, not claimed to be zeroed. The gate verifies the remaining stack, continuation, retained-cell and live-byte state, and requires cleanup release bytes to equal the invocation's allocated bytes for normal, quota and trap outcomes. This endpoint does not alter the compiler's default lowering selection.

Existing controls available to this lane are the independent source/kernel checker, exact typed ordered-stack interfaces, checked nominal IDs and shapes, runtime failure/quota reason and phase, ordered host request logging, construction/invocation status, `test.abort` for a terminal trap after a visible effect request, and the checked host-only runtime push/observe/metric ABI. The ABI exposes complete ordered stack cells and recipe observation, semantic source/program identity metadata, runtime allocation/release/live/peak metrics, memory bytes, steps, and request counters. The finite trial must compare the full observable stack, request prefix, identity and normalized recipe, plus outcome/quota/trap/cleanup and allocation/retained-memory counters; a matching printed final scalar is insufficient.

## Supported and unsupported measurements

Supported, when the retained runner observes them for both arms: exact module and tool digests; optimizer mode; source/checker identity and checked input interface; post-compilation runtime input values; complete ordered typed output stack; ordered effect/request prefix; normalized observable recipe and semantic program identity; guest logical allocation and release charges; Wasm linear-memory size (`memory_bytes`), retained-before-begin guest-cell bytes, post-execution cleanup live bytes; quota phase/reason; trap status; and cold/warm execution timing under a pinned engine and repeated inputs.

The selected production runtime is Node/V8 (`wasm32-core-on-node-v8`), not Wasmtime: `crates/noble-cli/src/core/runtime/config.json` pins Node 24.13.0/V8 13.6.233.17-node.37 and its WebAssembly feature flags, while `CoreEngine` executes through `WebAssembly.Module` and `WebAssembly.Instance`. The host ABI reports Wasm linear-memory size and guest retained bytes, not the Node/V8 process's complete resident set or allocator overhead. Engine/process RSS is therefore **unsupported**, not zero, and cannot support the decision. This finite resource-free run does not measure WIT canonical ABI ownership, resource cleanup, native pins, host authorization, physical-GC behavior, arbitrary source composition, or cross-engine portability. Those claims remain open and are not transferred from these results.

Pinned tool configuration is Rust 1.96 nightly, wasm-tools 1.245.1, Binaryen 125, and Node 24.13.0/V8 13.6.233.17-node.37 from the reviewed tool selection. Wasmtime 40.0.2 is selected only by the separate M3 comparison and is not the runtime for this trial. The retained receipt must also bind the exact source commit/tree, CLI/test executable digest, target and Wasm features, engine configuration, module hashes, workload input bytes, limits, and optimizer mode. Each required measurement runs only after its source commit is clean; raw output is retained outside the source tree until copied into a dated evidence commit.

## Frozen acceptance thresholds

These criteria are frozen before any ADAPT-17 baseline measurement. The result is **GO** only if every correctness/control criterion and every gain criterion below passes. Otherwise it is **NO-GO**; no default backend selection follows either result.

1. **Semantic/control agreement:** 100% exact agreement between the independently derived expectations and every arm/optimizer/workload run for complete ordered stack values and types, ordered host-request/effect prefix, semantic program identity, normalized observable recipe/captures, normal/trap/quota classification, quota phase/reason, and cleanup. No accepted output may omit a dynamically reachable recipe or change source preparation/request count. Unsupported observations are explicit and cannot count as passes. At allocation-limit boundaries, the expected allocation-quota versus normal result is derived from that arm's measured guest charge and the same declared limit; all other observations and cleanup remain exact.
2. **Allocation gain:** each statically eligible constructor/case specialization must save at least one 48-byte cell (48 guest logical allocation bytes) per eliminated transient variant wrapper. Across the complete four-workload × optimizer matrix, candidate total guest logical allocation charges, Wasm linear-memory size, and retained-before-begin guest-cell bytes must each not exceed baseline. A specialization that merely changes instruction spelling or is never reached does not count.
3. **Warm-time gain:** use seven measured warm repetitions after three warm-ups on the already compiled artifact in the same pinned Node/V8 process and configuration; compare medians. Candidate warm execution time must improve by at least 5% in at least two of the four workload families (averaged across optimizer settings), and no workload × optimizer cell may regress by more than 5%. Cold setup/compilation time is reported separately and cannot substitute for warm execution time.
4. **Boundary and failure controls:** for a workload with exactly one checked variant-wrapper allocation, run allocation limits 47/48/49 bytes (one below/at/one above the 48-byte baseline charge), and require the exact arm-specific status predicted by the measured guest charge with no leaked cells. Run a construction-quota refusal, an invocation-quota refusal, a runtime `test.abort` after a recorded ordered request prefix, and a malformed host-boundary value; verify the specified stage, preserved prefix/prior stack, and cleanup for both arms and both optimizer settings. The fixed invocation-quota form's initialization consumes seven metered ticks, so its seven-step budget admits initialization and must refuse the first dispatch tick in phase 1; smaller budgets would only test initialization refusal.
5. **Fallback and default:** every unsupported candidate shape is reported as baseline fallback and is checked against the baseline result. The default compiler path and ordinary CLI behavior remain unchanged, whether the trial is GO or NO-GO.

## Unit 4 rule

Constructor reuse is separate from transient constructor/case fusion. Do not infer uniqueness from last use. Reuse can be retained only if the checker proves no surviving alias through every root/shared tail/capture/observable recipe, the cell size/layout is known, and controls show allocation/trap cleanup parity. If that cannot be established, record a specific drop decision and retain the existing alias/capture controls; do not mutate a payload in place or claim zero allocation for a shared value.

### Recorded unit 4 disposition

Drop constructor reuse from this slice. `proofs/foundation/NobleFoundation/ConstructorReuse.lean` explicitly limits `reachableFrom` to one level and disclaims allocator, source-level ownership, Wasm-lowering, measurement, and runtime correspondence; its `shared_alias_control` proves that the same overwrite changes both observed occurrences, but does not prove that a real checked value has no transitive root, shared-tail, captured-Program, or observable-recipe alias. The selected type-directed candidate only removes a known transient Sum wrapper; it does not mutate a pre-existing payload or infer uniqueness. The frozen `shared-alias` control captures I64 `7`, duplicates that Program, wraps one alias in a Sum, and retains the other alias and recipe. This disposition makes no constructor-reuse or zero-allocation claim.

Reopen only with a source-checker-derived transitive ownership/reachability witness covering every live root and saved recipe, a model theorem matching that witness to the actual runtime cell layout and replacement semantics, and executed capture/shared-tail/observable-recipe plus quota/trap-cleanup controls. Last-use analysis or the current depth-one model alone is insufficient.
